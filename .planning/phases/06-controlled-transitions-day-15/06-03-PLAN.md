## Phase Goal

**As a** user of this agent chat, **I want to** have task state changes strictly validated against an explicit transition graph, **so that** the agent cannot silently skip, reverse, or resurrect lifecycle steps, and every refused attempt leaves a clear, explainable trace instead of a silent no-op or a crash.

<objective>
Make rejections visible on the human-driven surfaces: the manual Pause/Resume/Cancel buttons must refuse with an explained 4xx instead of silently succeeding, and the Tasks tab history timeline must show what the agent *tried* alongside what it actually did.

Purpose: the UI half of TRANS-02 (clear, explainable rejection in the UI), plus D-04, D-09 serialization, and D-11 rendering.
Output: rejection fields on the task API response, 409 Conflict handling on the three manual task endpoints, inline visually-distinct rejected rows in the Tasks tab (covering both edge-move refusals and pause/resume self-loop refusals), and REST tests covering all of it.
</objective>

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-06-01 | Information Disclosure | `pause_task_endpoint` / `resume_task_endpoint` / `cancel_task_endpoint` | mitigate | `_get_task_or_404(session, task_id, current_user.id)` stays the first statement in every endpoint, so a non-owner receives 404 before any legality evaluation can produce a 409 or persist a rejection row. A non-owner therefore cannot use the 404-vs-409 difference to learn another user's task state. Enforced by an explicit cross-user test asserting 404, not 409. |
| T-06-02 | Information Disclosure | 409 `detail` string | mitigate | `detail` is `str(exc)` — the server-built reason naming the task id, its current state, and legal next states for a task the caller owns. No traceback, no raw exception repr, matching CLAUDE.md's error-handling convention. |
| T-06-03 | Tampering (XSS) | `renderTaskHistory` rejected row (both edge-move and self-loop shapes) | mitigate | Rejected rows are written with `textContent` on freshly created elements; no `innerHTML`, no template-string HTML, so a reason containing markup renders as literal text. Asserted by an unchanged `innerHTML` occurrence count. |
| T-06-04 | Elevation of Privilege | Manual cancel of a finished task | mitigate | Terminal-state guard in `agent/tasks.py` (Plan 01) is the authority; the endpoint only translates the refusal to 409. The client cannot bypass it since no state value is accepted from the request body on these endpoints. |
| T-06-05 | Denial of Service | Concurrent manual operations on one task | accept | Pre-existing per-chat `asyncio.Lock` (`agent/state.py::chat_locks`) is acquired by all three endpoints and is left untouched by this plan. |
| T-06-06 | Denial of Service | Repeated manual refusals growing the history timeline | accept | Each refused button click appends one short, server-built row, serialized by the existing per-chat lock; the Tasks tab renders the list as-is. Bounded by human click rate; same disposition as Plan 01's T-06-06. |
| T-06-SC | Tampering | npm/pip installs | accept | Zero new packages; the frontend remains vanilla JS with CDN libraries only per CLAUDE.md's hard constraints. No bundler, no npm. |
