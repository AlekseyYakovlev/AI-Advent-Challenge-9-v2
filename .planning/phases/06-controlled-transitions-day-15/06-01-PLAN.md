## Phase Goal

**As a** user of this agent chat, **I want to** have task state changes strictly validated against an explicit transition graph, **so that** the agent cannot silently skip, reverse, or resurrect lifecycle steps, and every refused attempt leaves a clear, explainable trace instead of a silent no-op or a crash.

<objective>
Make the transition graph real in the one place it cannot be bypassed: the CRUD domain layer (`agent/tasks.py`). After this plan, an illegal transition attempted through *any* caller (LLM tool call, REST endpoint, or a future one) is refused, the task's state is untouched, and a `rejected=True` history row explains why.

Purpose: TRANS-01 (explicit allowed-transition set, illegal transitions rejected) and the graph half of TRANS-03 (pause/resume never violates the graph). Every later plan in this phase consumes the `IllegalTransitionError` and the rejection columns created here.
Output: Two new `TaskTransition` columns + idempotent migration, a directed-edge table and terminal-state set, `IllegalTransitionError`, legality gates on `transition_task`/`set_paused`/`cancel_task`, `build_transition_illegal_prompt`, and the tests proving all of it.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| LLM tool call → `agent/tasks.py` | The model chooses `task_id` and `new_state`; both are attacker-influenceable through chat content |
| Browser REST call → `agent/main.py` → `agent/tasks.py` | Authenticated user supplies an arbitrary `task_id` path parameter |
| Existing `app.db` on disk → `init_db()` | Schema drift between a deployed database and the current model definitions |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |

| T-06-01 | Information Disclosure | `agent/tasks.py::transition_task` / `set_paused` / `cancel_task` | mitigate | Keep `_get_owned_task(session, user_id, chat_id, task_id)` as the first statement in every one of the three functions; the legality check runs strictly after it, so a non-owner always receives `TaskNotFoundError` and can never distinguish "task exists in state X" from "task does not exist".
