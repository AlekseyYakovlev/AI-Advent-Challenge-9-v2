<objective>
Add "Редактировать" and "Удалить" buttons to every long-term memory entry in the sidebar memory panel, with an inline edit form (key + full value), a confirmed delete, and a draft that survives panel re-renders. Lock the safety rules with a Node-free source guard test.

Purpose: Phase 11 goal (ROADMAP): "the user must be able to edit long-term memory fields through the UI ("Редактировать" and "Удалить" buttons per entry)". The list is read-only today (`renderMemoryEntries` renders key + truncated value only).
Output: edited `ui/static/app.js` (state fields, seven new functions, two modified functions), new `tests/test_memory_panel_ui.py`. `ui/static/index.html` is NOT changed.
</objective>

<assumptions>
There is no CONTEXT.md and no UI-SPEC.md for this phase (user decision). The only locked input is the roadmap goal with the button labels "Редактировать" and "Удалить". The items below are assumptions adopted from 11-RESEARCH.md, not user decisions.

| ID | Assumption adopted from research | Effect in this plan | How to flip it |
|----|----------------------------------|---------------------|----------------|
| A1 | Both `key` and `value` are editable | The form has a key input and a value textarea; both are sent | Render the key as read-only text and send `{ value }` only |
| A2 | Inline edit in the sidebar, not a modal | No markup in `index.html`, no interaction with the Phase 10 x-only modal rule | A modal would need overlay id `<stem>-modal`, x button id `btn-close-<stem>`, x-only close (Phase 10 guard test) |
| A3 | Native `confirm()` before delete | Same convention as invariants / MCP / scheduler / chat delete | A custom confirm UI would be new work |
| A4 | No live cross-tab sync | A second tab shows the old list until its next chat answer or chat switch | Would need a `/ws/events` frame (out of scope) |
| P2 (planner) | One edit form at a time; pressing "Редактировать" on another entry replaces the current draft | A single `state.editingMemory` object | Keep a map of drafts by id |
| P3 (planner) | No keyboard shortcut (no Enter-to-save, no Escape-to-cancel) | No `keydown` listener is added, so Phase 10's rule "no Escape closer in app.js" cannot be violated | Add shortcuts after Phase 10 is settled |

Out of scope: editing working memory, an "add entry" button, bulk delete, undo, styling changes outside the long-term rows.
</assumptions>
