# Phase 20 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Scope.** Phase 20 is almost entirely backend. No new pages, modals, settings sections or design tokens. D-06 forbids any UI display of the effective limits. The UI surface is exactly three touchpoints in existing files, all of them message states:

1. Chat: WebSocket error frame `RATE_LIMITED` (D-05) -> toast, typed text stays in `#message-input`. Surface: `ui/static/app.js`, `case 'error'` of the WebSocket frame handler.
2. Chat: WebSocket "queued" frame (D-14) -> the existing loading bubble shows a queue caption instead of a silent wait. Surface: `ui/static/app.js`, `appendLoadingBubble` and the frame handler.
3. Login form: 429 lockout answer (D-09) -> message in the existing `#login-error` element. Surface: `ui/static/login.html`.

Not UI in this phase (explicitly out of contract): `/debug/routes` auth (LIM-04), HTTP 429 and `Retry-After` for HTTP clients, `stats` queue-wait field (D-15, API only), the verification script, the report, the manual second-device UI check (uses the existing UI unchanged). Everything else in `ui/static/` is locked as-is.

## Surface 1 — Rate limit in chat (D-05)

**Trigger.** The WebSocket sends `{"type": "error", "code": "RATE_LIMITED", "detail": ..., "retry_after": N}` (N = whole seconds until a slot frees).

**Behaviour** in the `case 'error'` branch of the frame handler, a new `else if (data.code === 'RATE_LIMITED')` before the generic fallback:
- `setStreaming(false)` and `removeLoadingBubble()` run as for every error (already at the top of the case).
- The text the user typed must remain available in `#message-input`. If the send path already cleared the input, restore it from `state.lastFailedMessage` when the input is empty (same pattern as the existing `PROVIDER_UNAVAILABLE` branch; set `state.lastFailedMessage` at send time). If the input already holds new text, do not overwrite it.
- Show `showToast('Слишком много сообщений. Повторите через ' + N + ' с', 'warning')`. N is taken from `data.retry_after`; the client builds the string itself so the wording is stable regardless of server `detail`. If `retry_after` is missing or not a positive number, fall back to `Слишком много сообщений. Повторите чуть позже`.
- No send-button lock, no countdown, no disabled input, no banner (D-05 explicit).
- The message was not stored by the server (D-04), so no tree reload is needed and no ghost bubble may remain: the optimistic user bubble, if the send path appended one, is removed (planner: verify against the send path; if the bubble is only rendered from the tree, nothing to remove).

**Toast duration.** Whatever `showToast` already uses; no new timing.

## Surface 2 — Queued generation (D-14)

**Trigger.** The server sends a new frame, name at the planner's discretion (recommended `{"type": "queued", "chat_id": ...}`), when the turn is waiting for a generation slot. The turn then proceeds to normal streaming (`token` frames) once a slot is taken.

**Behaviour.**
- While queued, the existing loading bubble (`appendLoadingBubble`, three `typing-dot`s) stays visible. Add one caption line inside the same bubble, under the dots: `<div class="queue-note mt-1 text-sm text-slate-400">В очереди, ожидание свободного места…</div>`. Created with `document.createElement` and `textContent` (static string, no `innerHTML` with dynamic data). Size is `text-sm` (14px), the declared Body role; `text-xs` is not used.
- The `queued` frame handler calls `appendLoadingBubble()` first if no streaming bubble exists yet (the frame may arrive before the first token), then adds the caption if absent (idempotent).
- The caption is removed as soon as the first `token` frame arrives (the existing `appendTokenToStream` path; add removal of `.queue-note` there) or on `done` / `error` / chat switch / Stop (all of which already call `removeLoadingBubble()`, which removes the whole bubble, so no separate cleanup is needed for those).
- Input and send controls behave exactly as during normal streaming (`isStreaming` true, Stop button available). Stopping while queued must cancel the turn through the existing stop path; the server must release the queue entry (backend concern, noted for the planner).
- No position-in-queue number, no timer, no estimated wait (not in the decisions; the queue is unbounded and waits are unpredictable).
- HTTP clients see no UI (D-14).

## Surface 3 — Login lockout (D-09)

**Trigger.** `POST /api/v1/auth/login` answers 429 with `Retry-After` and body `detail` + `code`. Same answer for existing and non-existing usernames, so the UI must not branch on username.

**Behaviour** in `login.html` submit handler, before the generic `body.detail || 'Ошибка входа'` fallback:
- If `resp.status === 429`: read `Retry-After` (seconds) from the response header; compute `minutes = Math.max(1, Math.ceil(seconds / 60))`; set `errorEl.textContent = 'Слишком много неудачных попыток. Повторите через ' + minutes + ' мин'`. If the header is missing or unparsable, fall back to `Слишком много неудачных попыток. Повторите позже`.
- Rendered in the existing `#login-error` (`text-sm text-red-400`), via `textContent`. No new element, no banner, no countdown, no form disabling: the user may press "Войти" again and receives the same message (a correct password is refused during the block, D-09).
- Minutes rounding rule: always round up, minimum 1 (so "через 1 мин" is shown for the last 60 seconds).
- CORS note for the planner: `Retry-After` must be readable from `http://<host>:8000` pages calling `:8001`; if the agent CORS config does not expose it, add it to `expose_headers`, otherwise the fallback text will always be shown. Alternatively the server may also put the seconds in the JSON body; the client prefers the header, then body `retry_after` if present.
- Wrong-password and network-failure messages (`Ошибка входа`, `Agent недоступен. Попробуйте позже.`) are unchanged.

Pluralisation: `с` and `мин` are abbreviations and do not decline, so no plural logic is needed.

## Interaction and Accessibility Notes

- The toast container is existing; do not add a second live region. If the existing toast container has no `aria-live`, adding `role="status"` to it is acceptable but out of scope here.
- The queue caption is plain text inside the bubble; screen readers read it when focus/virtual cursor reaches the bubble. No `aria-live` is added (avoids chatty announcements).
- `#login-error` already is the sole error region; add `role="alert"` to it (one-attribute change) so the lockout message is announced.
- Contrast: `text-slate-400` on `bg-slate-800` and `text-red-400` on `bg-slate-900` follow the existing project convention.
- Closing policy for modals (Phase 10, X-only) is untouched: no modal is added.

## Assumptions (non-interactive session)

- Rate-limit toast uses the `warning` type; the other WebSocket error toasts use `error`.
- The client builds the Russian strings from `retry_after` / `Retry-After` rather than displaying server `detail`, so wording is stable and testable.
- The queue indicator is a caption inside the existing loading bubble, not a new element type; the frame name `queued` is a recommendation, final name is the planner's call (CONTEXT: Claude's discretion).
- The caption disappears at the first streamed token.
- Login block shows minutes (rounded up, minimum 1); no live countdown; the form stays usable.
- `Retry-After` must be CORS-exposed for the login page to read it; fallback text exists if it is not.
- No UI exposes effective limits (D-06) and none is added for queue length or position.
- Manual UI check from another device (D-21) uses the existing UI and needs no UI change; the human checkpoint checklist belongs in the plans and report, not in this contract.
