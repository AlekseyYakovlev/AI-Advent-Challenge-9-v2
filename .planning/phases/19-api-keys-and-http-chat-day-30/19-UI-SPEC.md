# Phase 19 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Scope.** No new pages, no new design tokens. The UI surface is exactly three touchpoints:

1. A new "API ключи" section in the Settings modal (`#settings-modal`, `ui/static/index.html`) — D-20, D-22, D-24.
2. A new one-time key modal (`#api-key-modal`) shown after creation — D-21, D-22.
3. Handling of a new `/ws/events` frame so an HTTP-originated exchange appears in an open chat — D-15, D-19 (no visual marker, no badge).

Everything else in `ui/static/` is locked as-is. Follows the Phase 18 contract (`18-UI-SPEC.md`) for the Settings modal conventions.

## Settings Modal — "API ключи" Section Contract

**Placement (assumption).** New `<section id="api-keys-section" class="border-t border-slate-700 p-5 space-y-3">` placed after `#llm-providers-section` and before `#network-section` (CONTEXT code_context says "after `#llm-providers-section`"). Heading `<h3 class="text-lg font-semibold">API ключи</h3>` in a `flex items-center justify-between` header row with the button `#btn-api-key-add` (`rounded-lg bg-indigo-600 hover:bg-indigo-500 px-3 py-1.5 text-sm font-medium transition`) labelled "+ Создать ключ" (same shape as "+ Добавить сервер").

**Explainer line (D-22).** Directly under the header: `<p class="text-xs text-slate-500">` — "Ключ позволяет вызывать API из любого клиента: передавайте его в заголовке <code class="font-mono text-slate-300">Authorization: Bearer &lt;ключ&gt;</code>. Ключами нельзя управлять другими ключами." (The `<code>` is built with DOM nodes, not `innerHTML`.)

**Create form (`#api-key-form`).** Hidden by default, toggled by the header button; markup mirrors `#mcp-server-form`: `hidden rounded-lg bg-slate-800/50 border border-slate-700 p-3 space-y-3`.
- Field: label "Название" (`block text-sm text-slate-400 mb-1`), `<input type="text" id="api-key-name" maxlength="100">` with standard input classes + `focus:outline-none focus:ring-2 focus:ring-indigo-500`, placeholder "Например, ноутбук или скрипт". Hint `text-xs text-slate-500 mt-1`: "Название нужно только для того, чтобы вы отличали ключи в списке."
- Error line `<p id="api-key-form-error" class="text-xs text-red-400">`.
- Actions `flex justify-end gap-2`: "Отмена" (`rounded-lg px-4 py-2 text-sm text-slate-400 hover:text-white transition`) and "Создать" (`rounded-lg bg-indigo-600 hover:bg-indigo-500 px-4 py-2 text-sm font-medium transition`). Enter in the field submits.
- Validation: empty/whitespace name -> inline error "Введите название ключа" (no request). Submit button `disabled:opacity-50` while the request is in flight.
- On success: form hides and resets, list reloads, one-time modal opens.
- Cap (D-03): the server's refusal for >20 active keys is shown inline in `#api-key-form-error` using the server `detail`; assumption: the "+ Создать ключ" button is also disabled (`disabled:opacity-50 disabled:cursor-not-allowed`, `title`="Достигнут лимит: 20 активных ключей") when the loaded list has 20 items.

**List (`#api-key-list`, `space-y-2`).** One card per active key, built like `renderMcpServerRow`: `rounded-lg bg-slate-800 border border-slate-700 p-3 space-y-2`.
- Header row `flex flex-wrap items-center justify-between gap-2`: left = name (`text-sm font-semibold truncate`, `textContent`); right = "Отозвать" button (`px-2 py-1 text-xs text-red-400 hover:text-red-300 disabled:opacity-50 disabled:cursor-not-allowed`, `type="button"`, `aria-label`="Отозвать ключ {name}").
- Meta line `text-xs text-slate-500`: `<span class="font-mono text-slate-300">aia_3fK9…</span> · создан {date} · использован {date|«никогда»}`. Prefix is rendered exactly as returned by the server (server includes the ellipsis or UI appends `…`; planner's call, but the displayed form is `aia_` + first characters + `…`).
- Dates use the existing ru-RU formatter (`formatDate`-style `toLocaleString('ru-RU', ...)`, app.js ~813). Last-used shows "никогда" when null. No relative-time logic.
- All server-provided strings (name, prefix) set via `textContent`; if any HTML is ever required, `DOMPurify.sanitize()` (project rule). Key names are user input.

**States.**

| State | Rendering |
|-------|-----------|
| Loading | List area shows `text-sm text-slate-400` "Загрузка…" (replaced on load) |
| Empty | `<div id="api-key-empty" class="text-center text-slate-500 text-sm py-4">` — bold line "Ключей пока нет" + "Создайте ключ, чтобы обращаться к чату по HTTP из curl, скриптов или других программ." (same structure as `#mcp-empty`) |
| Populated | Key cards, newest first (assumption) |
| Load error | `text-sm text-red-400`: "Не удалось загрузить список ключей. Попробуйте открыть настройки ещё раз." |
| Revoking | Row's "Отозвать" button disabled until the request settles |

Data is fetched every time the settings modal opens (add `loadApiKeys()` next to `loadNetworkInfo()` in `openSettingsModal`). The calls are made with the session cookie via the existing `apiFetch` (key management is cookie-only, D-01).

**Revoke flow (D-24).** Native `confirm()` — the project's established destructive pattern (MCP/provider/KB/scheduler/invariant deletes all use `confirm`). Copy: `Отозвать ключ «{name}»? Все программы, использующие его, сразу потеряют доступ. Это действие нельзя отменить.` On OK: DELETE request, row removed from the list, toast `Ключ «{name}» отозван` (type `success`). On failure: `showToast(err.message, 'error')`. Revoking also re-enables "+ Создать ключ" if the cap had been reached.

## One-Time Key Modal Contract (`#api-key-modal`)

**Structure.** Copies the existing modal skeleton (`#add-user-modal` / `#kb-create-modal`): `<div id="api-key-modal" class="hidden fixed inset-0 z-[60] flex items-center justify-center bg-black/60" role="dialog" aria-modal="true" aria-labelledby="api-key-modal-title">` containing `bg-slate-900 border border-slate-700 rounded-xl shadow-xl w-full max-w-2xl mx-4 max-h-[90vh] overflow-y-auto`. Stacking assumption: it sits above the Settings modal (`z-50`), hence `z-[60]`; Settings stays open underneath.

**Close policy (Phase 10).** Closes ONLY via the × button (`#btn-close-api-key-modal`, `aria-label="Закрыть"`, `text-slate-400 hover:text-white text-xl leading-none`). No backdrop click, no Escape handler, no "Готово"/"Отмена" button. Opening the modal moves focus to the first Скопировать button (or the key block).

**Title:** "Ключ создан" (`text-lg font-semibold`).

**Body (`p-5 space-y-4`):**
1. Warning (`text-sm text-yellow-500`, `role="alert"`): "Скопируйте ключ сейчас — после закрытия этого окна он больше не будет показан. Если вы его потеряете, создайте новый ключ."
2. Key block: label "Ключ «{name}»" (`block text-sm text-slate-400 mb-1`), then a row `flex items-center gap-2`: `<code id="api-key-value" class="flex-1 rounded-lg bg-slate-800 border border-slate-700 px-3 py-2 text-sm font-mono break-all select-all">aia_…</code>` and a button "Скопировать" (`rounded-lg bg-indigo-600 hover:bg-indigo-500 px-3 py-1.5 text-sm font-medium transition shrink-0`).
3. curl example (D-22): label "Пример запроса" (`block text-sm text-slate-400 mb-1`); `<pre id="api-key-curl" class="rounded-lg bg-slate-800 border border-slate-700 px-3 py-2 text-xs font-mono overflow-x-auto whitespace-pre">` with a "Скопировать" button (same style) under or beside it. Hint `text-xs text-slate-500 mt-1`: "Подставьте номер чата, название модели и текст сообщения. Список чатов: GET /api/v1/chats."

**curl text.** Built client-side from `window.location.hostname` + `AGENT_PORT` (the agent address the UI uses: `AGENT_BASE`, i.e. the host the UI was opened from — D-22) with the real key substituted. Shape (path/field names finalised by the planner; this is the contract for layout, one flag per line with `\` continuation, single-quoted JSON body):

```
curl -X POST {AGENT_BASE}/api/v1/chats/{chat_id}/http-message \
  -H "Authorization: Bearer aia_…" \
  -H "Content-Type: application/json" \
  -d '{"content": "Привет!", "model": "{model}"}'
```

`{chat_id}` and `{model}` stay as visible placeholders (assumption: the modal does not guess them). The block is assigned via `textContent`.

**Copy interaction.** Reuse `copyTextToClipboard` (HTTP-safe: `navigator.clipboard` with hidden-`textarea` + `execCommand('copy')` fallback, Phase 18) — required because the UI is commonly opened over plain HTTP from a LAN IP. Feedback via `showToast`: success `Ключ скопирован` / `Пример запроса скопирован` (type `success`); failure `Не удалось скопировать в буфер обмена` (type `error`). No inline checkmark state change. Key text is `select-all` so manual copy also works.

**Lifecycle / security.** The full key lives only in a local variable and the `#api-key-value` / `#api-key-curl` nodes. On close: clear both nodes' `textContent`, null the variable, never store in `localStorage`, `state`, logs or URLs.

## HTTP-originated Messages in the Existing Chat UI (D-15, D-19)

- **No visual distinction.** Messages that arrived over HTTP render through the existing message renderer exactly like typed ones: no "API" badge, no new column, no icon. (Deferred idea, per CONTEXT.)
- **New events frame.** The server publishes one frame at the end of an HTTP turn on `/ws/events`. Contract with the planner: frame carries at least `type` (name is planner's call, recommended `chat_updated`) and `chat_id`. Handled in `handleEventFrame` (app.js ~3371) next to `chat_title_updated`, before the `applySchedulerEvent` fall-through.
- **Frontend behaviour on frame:**
  - Always refresh the chat list (`loadChats()`), so new title and order appear (title text updates through the existing `$('chat-title')` path).
  - If `frame.chat_id === state.currentChatId` AND no local WebSocket turn is in progress (assumption: reuse the existing streaming/in-flight flag the send path sets), re-fetch the tree (`GET /api/v1/chats/{id}/tree`) and re-render messages, stats and scroll to bottom exactly as when selecting a chat. If a local turn is streaming, skip the re-read (the local turn's own `done` frame re-renders) so the in-flight stream is not disturbed.
  - Frames for other chats only refresh the list; no toast, no unread badge (assumption — keep minimal).
- **No in-progress indicator, no input lock** for HTTP turns (D-19). The send box and Stop button behave unchanged.
- **Busy chat.** If the user sends from the UI while an HTTP turn holds the chat lock, the existing WebSocket path simply waits (D-16, unchanged); no new UI state.

## Assumptions (non-interactive session)

- Section placed between "Провайдеры LLM" and "Сеть" (CONTEXT says after `#llm-providers-section`; "Сеть" stays last as in Phase 18).
- One-time modal uses `z-[60]` so it overlays the still-open Settings modal; no other modal stacking is changed.
- Revoke uses native `confirm()` (project convention) rather than a custom confirmation modal.
- Key list sorted newest first; dates formatted with the existing ru-RU formatter; last-used null -> "никогда".

- Name is required, max 100 characters (maxlength on input; server limit is the planner's call).
- curl example uses `{chat_id}` and `{model}` placeholders; the endpoint path in the example is illustrative and must match the planner's final route.
- Event frame refreshes the open chat only when no local turn is streaming; no unread indicator for other chats.
- No client-side persistence of keys of any kind.
