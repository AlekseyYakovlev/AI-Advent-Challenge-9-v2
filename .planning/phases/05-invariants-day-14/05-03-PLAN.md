<objective>
Make the invariants bite: after the agent answers, a second LLM call reads its own full turn against the chat's active rules; if something conflicts, the agent is sent straight back to justify or retract it, the flagged rule and the justification are written down, and the user sees an amber banner under that exact message plus a count on the Инварианты tab.

Purpose: INV-04 is the requirement that makes invariants more than decorative prompt text — it demands a dedicated check that makes the LLM *act* on the conflict, not just annotate it after the fact. INV-05's second half (surfacing conflicts) rides on the same persisted record so the banner and the badge can never disagree.
Output: `InvariantConflict` table, the self-critique/justify-retract helpers in `agent/invariants.py`, the new sequencing inside `agent/ws.py::_handle_chat_message`, `GET /api/v1/chats/{chat_id}/invariant-conflicts`, the inline banner + tab badge, and two new test modules.

**Decisions this plan locks (resolving 05-RESEARCH.md's three Open Questions — these are engineering mechanics inside D-09/D-12/D-13, not new product scope):**
- **OQ1 — append, not replace.** The justify/retract reply is appended to `assistant_text` (matching the existing post-tool-result follow-up shape, so the streamed bubble and the persisted `Message.content` stay identical) AND captured separately into `InvariantConflict.note`. Replacing would silently destroy the flagged content the audit trail exists to record.
- **OQ2 — always critique when the chat has at least one active invariant, regardless of whether tools fired; skip the call entirely when the active set is empty.** D-08 puts prose in scope; the empty-set skip changes no observable behaviour and avoids paying for an LLM call that has nothing to check.
- **OQ3 — the badge counts every conflict recorded for the chat.** No `resolved`/`acknowledged` column: nothing in D-01..D-13 asks for dismissal, and D-13 frames the table as a persisted log.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| LLM → Agent (critique response) | The critique call's JSON is model-generated and fully untrusted: `conflict`, `invariant_scope` and `invariant_id` are all attacker/hallucination-controllable and reach the database |
| LLM → browser DOM (justification text) | `InvariantConflict.note` is LLM-authored prose rendered into the chat stream |
| Browser → Agent REST | `chat_id` on the conflicts route is attacker-controlled |
| Extra LLM round-trips → cost/latency | Each turn under active invariants now spends one extra non-streaming call, plus a second streamed call when flagged |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-05-12 | Tampering | `parse_critique_json` / `match_flagged_invariant` | mitigate | The critique's cited `invariant_scope`+`invariant_id` must match an entry in the already-resolved `active` set or the flag is dropped, so a hallucinated or attacker-steered id can never be written to `InvariantConflict` or rendered in the UI. Covered by `test_critique_hallucinated_invariant_id_is_ignored`. |
| T-05-13 | Tampering | conflict banner rendering in `buildConflictBanner` | mitigate | `invariant_title` is assigned with `textContent`; the LLM-generated `note` goes through `renderMarkdown()`, which is `marked.parse` piped into `DOMPurify.sanitize` — the same pipeline every assistant bubble already uses. | T-05-14 | Denial of Service | unbounded critique/justification text | mitigate | The critique call is capped at `max_tokens=512`; `InvariantConflict.note` is `max_length=2000` and truncated in `record_conflict` before the insert; the justify/retract call reuses the chat's existing `max_tokens` setting. |
| T-05-15 | Denial of Service | a hanging or erroring critique call stalling the per-chat lock | mitigate | `complete_chat` runs under the existing `settings.LLM_TIMEOUT` httpx timeout, and `run_self_critique` catches every exception and returns `{"conflict": False}`, so the lock is released and `done` is still sent.
