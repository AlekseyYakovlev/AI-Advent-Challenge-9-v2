<objective>
Build the background job that adds files to a ready knowledge base without ever taking it out of the ready state: chunk and embed only the new files, then in one short transaction insert the new rows, remove the replaced ones, patch a copy of the FAISS index and swap it in atomically.

Purpose: KBUP-05 and KBUP-06. The existing job (`run_index_job`) and its failure path (`_fail`) re-chunk every document and delete every chunk of the base, so neither may be reused for an addition.
Output: storage helpers, an optional `add_summary` key on the progress frame, `run_add_job` with its own non-destructive failure path, orphan recovery for an interrupted addition, tests.

Decisions locked by this plan (Claude's Discretion: "How the index is updated on addition and replacement"):
- The index is patched incrementally (`remove_ids` + `add_with_ids` on a copy read from disk); vectors of untouched documents are never recomputed.
- "Addition running" is signalled with `status == ready` and `phase == PHASE_ADDING`; no new column.
- A failed addition stores its message in `KnowledgeBase.error` on the ready base; the next addition clears it.
- The summary is transient: it travels once in the final frame as `add_summary` and is not stored.
- The addition job shares the single-slot indexing semaphore with index jobs (LM Studio serves one embedding model at a time).
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| add route -> background job | The job receives staged files and a classification computed from untrusted uploads |
| job -> SQLite + index file | Two stores must change together; a crash, error or cancellation can fall between them |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-21-09 | Tampering / Denial of Service | Failed or cancelled addition leaving partial rows or a destroyed base | mitigate | Dedicated `_fail_add` that never deletes chunks, never sets FAILED and never removes the index; embedding happens before any write; one transaction with rollback; tests `test_embedding_failure_leaves_base_untouched`, `test_failure_during_commit_rolls_back`, `test_shutdown_during_add_keeps_base_ready` |
| T-21-10 | Tampering | Rowid reuse pairing an old vector or an old citation with new text | mitigate | New documents and chunks are inserted before replaced ones are deleted inside the same transaction; `test_add_new_file_keeps_old_chunks_and_extends_index` asserts every new chunk id exceeds every old id |
| T-21-11 | Denial of Service | Index file and database disagreeing (`ntotal != chunk_count`) so the base reports a corrupt index | mitigate | `ntotal` checked against the counted rows before commit; pending file written before commit; commit, `os.replace` and cache swap run back-to-back with no await, shielded from cancellation |
| T-21-12 | Denial of Service | Process crash in the instant between commit and `os.replace` | accept | Window is a single synchronous rename after the heavy write is already on disk; outcome is the existing "index corrupt, delete and recreate" message; no data of other bases is affected |
| T-21-13 | Denial of Service | Base stuck in "adding" after a restart, or staging files accumulating | mitigate | `recover_orphaned_kb_jobs` clears `phase` on ready bases, sets a readable error, removes the staging root and unreferenced upload files; `test_recover_interrupted_addition` |
| T-21-14 | Information Disclosure | Progress and summary frames reaching another user | mitigate | Frames are published with `hub.publish(user_id, ...)` using the owner id passed by the route; existing `test_frames_reach_only_the_owner` keeps passing |
| T-21-15 | Denial of Service | Addition holding the SQLite write lock during embedding, model load or file moves | mitigate | No session is open across `ensure_embedding_model`, `_embed_all` or the staged-file moves; all of them finish before `_commit_addition` opens its transaction; `test_commit_section_holds_no_slow_calls` |
| T-21-38 | Denial of Service | `_commit_addition` running `patch_index` and `write_index_pending` inside the open write transaction, so other writers of the Agent (chat messages, settings) wait behind the SQLite single-writer lock | accept | The ordering is required: FAISS vector ids are `KbChunk.id` values that exist only after the inserts are flushed (T-21-10), and the pending index must be on disk before the commit so that database counts and index file can disagree only for one rename (T-21-11, T-21-12); moving the index work after the commit would widen that window to the whole write. Exposure is bounded: the section does no network or embedding work, its cost is one read, one in-memory patch and one write of a flat index (tens of megabytes at most for a base built under the 100 MB upload cap), readers are never blocked (WAL) and waiting writers have `busy_timeout` 5 s. Residual risk: on a very large base a writer could time out with "database is locked". It is made visible, not prevented: `commit_seconds` in `kb_add_ready` and the warning `kb_add_commit_slow` above `ADD_COMMIT_WARN_SECONDS` |
