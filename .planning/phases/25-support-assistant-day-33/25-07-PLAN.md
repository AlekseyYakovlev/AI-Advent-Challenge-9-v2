## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| WebSocket / HTTP client → command turn | authenticated user text, possibly with identifier |
| support server data → prompt | fenced ticket data (plan 05) enters the user-side message |
| model → tools | model may call support tools only from the chosen whole servers |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-25-30 | Denial of Service | notices and rate limit | mitigate | Notices resolved before the rate limit and the chat lock (as /help) and never stored; real turns go through the existing limiter and the generation queue (`run_limited_turn`) |
| T-25-31 | Tampering | HTTP `kb_id` with /support | mitigate | `apply_chat_kb` skipped for /support, so the chat's RAG config cannot be changed through a command turn |
| T-25-32 | Elevation of Privilege | tool exposure | mitigate | Model only gets `tools.allowed_tools` and the chosen servers' schemas from `build_support_tools`; direct lookup uses only the caller's `support` row |
| T-25-33 | Tampering | prompt injection via ticket text | mitigate | Block from `support_lookup.fence_support_data` merged before `Вопрос:` in the user message (never system); test asserts `<support_data>` placement |
| T-25-34 | Information Disclosure | logs | mitigate | `support_turn_done` logs ids and counts only |
| T-25-35 | Repudiation | direct MCP call visibility | mitigate | Direct call emitted as an ordinary `tool_call` frame and stored first in `tool_trace`, so every MCP use is visible |
</threat_model>
