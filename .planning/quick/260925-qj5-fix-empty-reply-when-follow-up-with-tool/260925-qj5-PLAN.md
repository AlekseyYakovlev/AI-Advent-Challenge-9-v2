<how_the_loop_knows_today>
All follow-ups after the first tool round go through `agent/ws.py::_run_tool_rounds` (line ~383):

- Each iteration: `_dispatch_round(...)` (increments `acc.rounds`), then
  `tools = turn.tool_schemas if acc.rounds < MAX_TOOL_ROUNDS else None` (None = cap reached,
  logs `tool_rounds_capped`), then `text, next_calls = await _stream_follow_up(turn, tools)`
  and `acc.text += text`.
- `_stream_follow_up(turn, tools)` returns `(text, tool_calls)`. `text` is EXACTLY what was
  sent to the client: every chunk goes through `_emit_filtered` (TraceLeakFilter.feed) and
  the tail through `_flush_filtered`, and only the returned safe strings are concatenated.
  `tool_calls` is the list from the `tool_calls` event (empty list if none). With
  `tools=None` it is a text-only stream and always returns `[]` for tool_calls.
- Loop detection: if `next_calls` share a signature with the previous round's `calls`, it logs
  `tool_loop_detected` and runs `_stream_follow_up(turn, None)` (the tools-less final
  follow-up), appends its text to `acc.text` and forces `next_calls = []`.
- `if not next_calls: return acc` ends the loop; otherwise `calls = next_calls`,
  `echo_text = text` and the next round runs. Exceptions set `acc.error` and return.
- The caller (`_handle_chat_message`, line ~674/692) does `assistant_text += rounds.text` with
  NO separator, so an empty follow-up adds nothing ("\n\n" is only used by the unrelated
  action-claim retry path at line ~654, which is out of scope).

So the check point is: right after the tools-ENABLED `_stream_follow_up(turn, tools)` call,
using its returned `text` (post-filter, emitted) and `next_calls`.
</how_the_loop_knows_today>

In `agent/ws.py` only:

2. Add a new private helper right after `_stream_follow_up`, named `_stream_follow_up_with_empty_retry(turn: _ToolTurn, tools: list[dict[str, Any]] | None, acc: _ToolRoundsResult) -> tuple[str, list[dict[str, Any]]]` with a one-line docstring. Behaviour: call `_stream_follow_up(turn, tools)`, append the returned text to `acc.text`. Then, if and only if ALL of: `tools` is truthy (a tools-enabled follow-up; the cap follow-up with `tools=None` never retries), the returned tool_calls list is empty, `not text.strip()` (measured on the emitted, post-TraceLeakFilter text returned by `_stream_follow_up`), and `not acc.empty_retry_used` — set `acc.empty_retry_used = True`, log `logger.info("tool_followup_empty_retry", chat_id=turn.chat_id, round=acc.rounds)`, call `_stream_follow_up(turn, None)` (the same tools-less path used by the cap and `tool_loop_detected`), append its text to `acc.text`, and return `(retry_text, [])`. Otherwise return the original `(text, tool_calls)`. Do not add any fallback text, separator or error when the retry is also empty. Do not catch exceptions here — they propagate to the existing `except Exception` in `_run_tool_rounds` (same LLM_ERROR behaviour as any failed follow-up).

3. In `_run_tool_rounds`, replace the two lines `text, next_calls = await _stream_follow_up(turn, tools)` / `acc.text += text` with a single `text, next_calls = await _stream_follow_up_with_empty_retry(turn, tools, acc)` (the helper already appends to `acc.text` — do not append twice). Leave the loop-detection branch, cap logic, error handling, `echo_text = text` and everything else untouched. Because the retry always returns `[]` calls, the loop then ends via `if not next_calls: return acc`; results/calls/rounds are not touched by the retry so tool_trace / memory_writes / task_writes aggregation is unchanged.

Do not modify the first stream, `_stream_action_claim_retry`, `_handle_chat_message`, `TraceLeakFilter` or `MAX_TOOL_ROUNDS`. Keep type hints, stdlib-first imports (no new imports needed), structlog snake_case event, helper under ~20 lines.
