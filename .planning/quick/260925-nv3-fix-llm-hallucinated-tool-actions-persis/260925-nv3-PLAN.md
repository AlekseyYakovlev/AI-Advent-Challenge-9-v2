<objective>
Stop the local LLM from hallucinating tool actions ("Файл создан" with no tool call) by:
(1) persisting each turn's tool calls + results on the assistant Message and replaying them (compact, truncated) in later turns' context;
(2) adding a short tool-use rule to the system prompt only on turns where tools are offered;
(3) a bounded one-shot corrective re-prompt when the model claims a completed action without calling any tool;
(4) raising Context Length to max 32768 / default 16384.

Purpose: evidence from logs/agent.log chat 35 (qwen3.5-9b + filesystem MCP) — turns 2-4 had no tool call yet claimed success because earlier turns' history showed "success" text with no visible tool call.
Output: code changes in agent/ws.py, agent/context_engine.py, agent/tool_guard.py (new), shared/models.py, shared/database.py, agent/schemas.py, UI settings, docs; new tests; full suite green.
</objective>

<design_decisions>
DD-1 (history format — compact text, NOT OpenAI tool messages). Reason: `_apply_compression_strategy` slices the history list by index (sliding = last 10, truncate_middle = first 2 + last 10, sticky = first + last 10). If one DB assistant row expanded into an `assistant{tool_calls}` dict plus N `tool` dicts, a slice could keep a `tool` message while dropping its `assistant.tool_calls` parent, which providers reject with HTTP 400; also `_message_tokens` and `compute_chat_stats` read `msg["content"]` as a string and would break on `content: None`. The compact text form keeps one dict per DB row, so every strategy, the tree walk, branching and stats work unchanged. The in-turn echo (`_normalize_tool_calls_for_echo` + `role: tool` messages inside the same turn) stays exactly as it is.
DD-2 (storage). New nullable `Message.tool_trace: str | None` (JSON text) on assistant rows only; NULL for every turn without tool calls. `Message.token_count` keeps counting only `content` (unchanged). Trace is not exposed in REST responses (UI unchanged).
DD-3 (replay token accounting). In `_load_branch_messages`, for rows with a trace the dict's `token_count` = stored token_count + tokens of the rendered trace, so usage% / no_compression overflow reflect what is actually sent. Consequence: `total_response_tokens` in stats includes trace tokens for tool turns only; turns without a trace are identical to today.
DD-4 (rule placement). The rule is appended in ws.py to `llm_messages[0]["content"]` (the system message) only inside `if tool_schemas:`; `build_system_prompt` is NOT changed, so `compute_chat_stats` and no-tools turns are unaffected.
DD-5 (guard placement). The guard runs right after the first stream and BEFORE the existing `if pending_tool_calls:` block, so a tool call produced by the retry flows through the existing dispatch + follow-up path with no duplicate code. Retry is streamed to the client and appended to `assistant_text`, same as the existing `transition_illegal` and invariants justify/retract re-prompts. No re-check after the retry (hard bound: one retry).
DD-6 (context_length DB rows). No data migration: existing global/per-chat rows keep whatever value the user has (including legacy 4096 defaults or values above 32768 saved under the old le=131072 limit — the slider clamps them on display, and the next save stores <= 32768). Only the model default, the ALTER TABLE default for DBs missing the column, the API validator, the stats default arg and the UI change. LM Studio load path: UI sends no context_length (`app.js` load-model body is `{model_id, gpu_offload}`) and `ModelLoadRequest.context_length` is LM Studio's own load parameter — left unchanged.
</design_decisions>
