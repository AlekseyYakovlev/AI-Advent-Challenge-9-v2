User request (Russian): "при первом вызове инструмента надо автоматически подключать MCP" — the user must not have to
press "Подключить" in Settings before the chat can use MCP tools.

## Why it must happen at turn start
The model can only call tools that are in the tool list sent to it, and a server's tool list is only known after connecting.
So when a chat turn builds its toolset (agent/mcp_tools.py `build_mcp_toolset`, called from agent/ws.py `_load_mcp_toolset`),
lazily connect the CURRENT USER's enabled MCP servers that have no live session, then expose their tools as usual.

## Design (decided — implement this)
1. agent/mcp_client.py: add `async def ensure_connected(user_id, server_id, command, args, env, cwd) -> McpConnectResult`.
   Under the existing per-(user_id, server_id) lock (`_lock_for`):
   - live session exists -> return its result WITHOUT replacing/closing it (unlike `connect_server`, which replaces — two
     concurrent chat turns must not tear down each other's session);
   - a failure is remembered in `_last_results` for that key -> return it WITHOUT retrying (no reconnect attempt on every
     chat turn; the user retries via Settings "Подключить"; editing/disconnecting a server already clears the remembered failure);
   - otherwise `open_session` (existing single MCP_CONNECT_TIMEOUT-bounded handshake); register the handle in `_sessions` on
     success, or remember the failure in `_last_results`.
   Do NOT call `get_status`/`_is_alive` on this path. Add a small sync helper if needed (e.g. `has_recorded_failure`);
   keep the public surface minimal.
2. agent/mcp_tools.py `build_mcp_toolset`: before reading live tools, for each ENABLED row of the user's servers with no live
   tools and no remembered failure, connect them CONCURRENTLY with `asyncio.gather(..., return_exceptions=True)` using
   `ensure_connected` with command/args/env/cwd derived from the row via agent.mcp_config (`load_args`/`load_env` — same as
   the REST connect handler in agent/main.py; do not duplicate parsing logic differently). Tool-call execution stays strictly
   sequential elsewhere; only the connect fan-out is concurrent. Any exception/failed connect must never break the chat turn
   (log a warning with ids + error code/type only; never env values/args) and simply contributes no tools. Emit an info log per
   auto-connect attempt (user_id, server_id, outcome, duration_ms).
3. shared/config.py: new `MCP_AUTO_CONNECT: bool = True` (document in .env.example). When False, behavior is exactly as before
   (manual connect only).
4. Cross-user isolation: only the chat owner's servers (`list_servers(session, user_id)`); disabled servers ("Включён"
   unticked) are never auto-connected.
5. UI: no new UI required, BUT verify the Settings list reflects auto-connected servers (it loads status from the REST status
   endpoint when the modal opens — confirm and note in SUMMARY; if a tiny change is needed keep app.js CRLF-safe and
   textContent-only).
6. Tests (pytest; fixture server tests/fixtures/mcp_stdio_server.py; never use ports 8000/8001):
   - auto-connect happens for an enabled unconnected server and its tools appear in the toolset;
   - second call reuses the session (no second process spawn, session object unchanged);
   - concurrent turns don't replace the session;
   - a failing server (bad command) is attempted once and NOT retried on the next turn (until disconnect/edit clears it), and
     its failure does not block other servers or the chat;
   - disabled server never auto-connected; other user's servers never touched;
   - MCP_AUTO_CONNECT=False keeps old behavior;
   - end-to-end WS chat turn (mocked LLM, like tests/test_mcp_chat_ws.py) where the server was configured but NOT connected
     beforehand and the tool call still succeeds;
   - real filesystem.exe (extend tests/test_mcp_real_filesystem.py or add a sibling, same skip pattern) with NO prior connect:
     configure -> build toolset (auto-connect) -> dispatch `list_allowed_directories`, assert `AiAdventAgentV2` in the result
     and no filesystem.exe from the run left alive (protected pre-existing PIDs must never be touched).
7. Docs: one short paragraph each in docs/ARCHITECTURE.md and docs/API_SPEC.md (env setting + behavior: connects lazily at the
   first chat turn, failures not retried until manual reconnect/edit, first turn may be delayed up to MCP_CONNECT_TIMEOUT).
