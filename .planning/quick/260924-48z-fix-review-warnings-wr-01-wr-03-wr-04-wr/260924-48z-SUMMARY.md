  owner task, awaits it (suppressing CancelledError/Exception), closes `errfile`, and re-raises.
- **Evidence:** the new test fails on the old code (verified by restoring the old `mcp_client.py`
  temporarily) and passes on the new one.
- **Tests:** `test_cancelled_open_session_leaves_no_child_and_no_registration` cancels a
  `connect_server` stuck in the `hang` fixture. It identifies the fixture child by psutil
  (children of the test process only, diffed against a pre-spawn snapshot), then asserts that exact
  pid+create_time is gone within 5 s and that nothing is in `_sessions` / `_last_results`.

### WR-05 unlocked get_status / cleanup_server
- **Changed:** `get_status` keeps the healthy path lock-free and takes `_lock_for(key)` only for a
  dead probe, re-checking `_sessions.get(key) is handle`; if not, it returns a new non-pinging
  `_registry_status(key)` and writes nothing. `disconnect_server` body moved to
  `_disconnect_locked`; `cleanup_server` runs it and deletes the lock entry while holding the lock
  (`if _locks.get(key) is lock`).
- **Evidence:** the two interleaving tests fail on the old code, pass on the new.
- **Tests:** disconnect-wins and reconnect-wins interleavings (test holds the lock, starts
  `get_status`, mutates the registry, releases), `cleanup_server` lock removal, and cleanup racing
  a connect in both orders (registry consistent, no exception).

### WR-06 ping timeout kills busy servers
- **Changed:** `_is_alive` replaced by `_probe` returning `alive | unresponsive | dead`. Dead means
  finished owner task, closed handle, no session, an anyio closed/broken/end-of-stream error, a
  process-gone OSError, or an `McpError` containing "Connection closed". A timeout or other error
  yields one `await asyncio.sleep(0)` re-check and is otherwise "unresponsive": the session is kept,
  status stays CONNECTED, and `mcp_ping_unresponsive` is logged (warning, ids and exception type
  name only). `list_mcp_servers` now uses `asyncio.gather(..., return_exceptions=True)`; a failing
  status check is logged (`mcp_status_check_failed`) and shown as a PROTOCOL_ERROR connection for
  that server only, order preserved, non-Exception BaseExceptions re-raised.
- **WR-06 probe result (empirical, run before implementing):** a `die_after` server connected, then
  pinged 2.5 s later after its process had exited: `send_ping()` raised
  `anyio.ClosedResourceError` **immediately (0.0 s)**, and the owner task did **not** finish (still
  not done after 0.5 s). So the review's premise for detecting death (owner task finishes) does not
  hold for a real crash; dead-process detection has to come from the stream error. Because that
  error is immediate and distinct from a timeout, the primary approach works and the
  `MAX_PING_FAILURES` consecutive-timeout fallback was not needed and not added.
  `test_get_status_detects_exited_process` stays green unmodified.
- **Tests:** `slow_ping` fixture (3 s blocking ping, `LIVENESS_TIMEOUT` patched to 0.5) stays
  CONNECTED across two checks and is never closed; `die_after` still reports PROCESS_EXITED, in
  under `LIVENESS_TIMEOUT`; three unresponsive servers listed through the API in under 1.3 s (all
  CONNECTED); one raising `get_status` yields 200 with that server as an error and the other still
  connected. The busy/concurrent/list tests fail on the old code.
- `ensure_connected` / `is_connected` are untouched (they never ping); `test_mcp_auto_connect.py`
  passes.

### WR-08 error classification and stderr tail
- **(a) Choice:** added a new enum member `McpErrorCode.SPAWN_FAILED`. Safe because
  `renderMcpError` (app.js) renders the server-provided `error_message`, `detail` and
  `stderr_tail` and never branches on `error_code`; `agent/mcp_tools.py` and
  `scripts/mcp_list_tools.py` only read `.value`; grep found no test/code/doc asserting exactly four
  codes.
- `classify_mcp_error`: order is TimeoutError, process-gone errors, `FileNotFoundError` ->
  COMMAND_NOT_FOUND, other `OSError` -> SPAWN_FAILED, "Connection closed", PROTOCOL_ERROR. New
  `spawn_failure_reason` yields `[errno N] strerror (winerror W)` only, never filename or env.
  Message: "Не удалось запустить процесс сервера: {reason}." `build_error_result` gained a
  keyword `reason`.
- `open_session` validates `cwd` with `os.path.isdir` before creating any handle/task/temp file and
  returns a SPAWN_FAILED result with "Рабочая папка (cwd) не найдена или не является папкой: <cwd>".
- Observed real messages on this machine: a text file as command -> `[errno 8] ... (winerror 193)`;
  a directory as command -> `[errno 13] ... (winerror 5)`; missing cwd -> the cwd message.
- **(b)** `read_stderr_tail` reads on the binary layer: `seek(0, END)`, start at
  `max(0, size - 64 KiB)`, bounded `read(size - start)`, decodes with `errors="replace"`, drops the
  partial first line when start > 0, and returns "" on OSError/ValueError/AttributeError.
- **Not fixed (as the plan states):** the stderr temp file itself is not size-capped, so a chatty
  long-lived server can still grow it without bound; only the read is bounded.
- **Tests (in tests/test_mcp_client.py):** SPAWN_FAILED for missing and file-as-cwd with no fixture
  child spawned; missing command with valid cwd still COMMAND_NOT_FOUND with the unchanged message;
  `PermissionError`, `OSError(193)`, `NotADirectoryError` -> SPAWN_FAILED,
  `ConnectionResetError`/`BrokenPipeError` still PROCESS_EXITED, wrapped in an ExceptionGroup too;
  a secret env value absent from message, detail and stderr_tail; tail read on a >128 KiB file via a
  spy proving no read exceeds 64 KiB and the result is the last 20 whole lines; partial-line drop;
  small and closed files. Existing assertions in `test_classify_mcp_error_unwraps_nested_groups`
  were kept and only extended.

### WR-04 child processes orphaned on hard Agent kill
- **Outcome: mitigated by the SDK job object; no code fix by us.** `mcp/os/win32/utilities.py`
  (mcp 1.30) `create_windows_process` (line 136) calls `_create_job_object()` (line 233; sets
  `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` at line 244) and `_maybe_assign_process_to_job` (line 252).
  The Agent holds the only job handle, so TerminateProcess of the Agent makes Windows kill the job.
- **Evidence contradicts the review for the fixture-only assumption:** the plan's `ok` fixture exits
  on its own when stdin closes (FastMCP stops on EOF), so a test using only `ok` would pass even
  with no job object and prove nothing. I confirmed this with a negative control (below). To make
  the test discriminating I added a `stubborn` fixture mode (handshakes, then survives stdin EOF for
  up to 60 s) and parametrized the test over `ok` and `stubborn`.
- **Negative control (scratch script, not committed):** with `win32job.CreateJobObject` patched to
  raise via a `sitecustomize` in the helper's PYTHONPATH, the `stubborn` child **survived** the hard
  termination of its parent (verified by pid+create_time, then killed by pid); with the job object
  active the same test passes. So the test really proves the job object.
- **Test:** `tests/test_mcp_orphan.py` (win32-only, skipped elsewhere) launches
  `tests/fixtures/mcp_orphan_helper.py` (opens a session, prints `CHILD_PID=`, idles), verifies the
  child by cmdline (fixture path + mode) and by the helper's pid among its parents, records
  create_time, hard-terminates only the helper exactly like `ui/supervisor.py::_shutdown_agent`,
  and asserts that pid disappears within 5 s. `finally` kills only the helper and only a pid whose
  create_time still matches. Both parametrizations pass.
- **Correction to the plan's note:** the plan said that if `win32job` cannot be imported the SDK
  only logs a warning. In the installed SDK `import win32job` is unconditional on win32 (line 25),
  so an import failure would break the SDK outright; only job creation or assignment failures
  degrade to a warning. The docs paragraph states the accurate version.
- Docs: "Child processes on Agent restart" paragraph added to `docs/ARCHITECTURE.md`.

### WR-01 no request-origin defense on mutating MCP routes

  and `require_json_content_type` (415 unless the media type is `application/json`; a missing
  Content-Type is rejected). Applied via `dependencies=[Depends(...)]` to create and update (both
  dependencies) and delete, connect, disconnect (origin only). GET routes and non-MCP routes are
  untouched. Log key `origin_rejected` (origin value and path only).
- **UI check:** `apiFetch` (app.js:76) always sends `Content-Type: application/json`; the UI page
  origins `http://localhost:8000` / `http://127.0.0.1:8000` are both in `CORS_ORIGINS`. The e2e
  script drove create/connect through a real browser context with `Origin: UI_URL` and passed.
- **Tests (tests/test_mcp_origin.py, 27 cases):** foreign Origin gives 403 on each of the five
  routes with no side effects (no server created, row unchanged, row survives delete, no connect,
  connection survives disconnect); `Origin: null` rejected; both allowed origins pass on all five
  routes; missing Origin passes on all five; GET list/status ignore a foreign Origin; text/plain
  and missing Content-Type give 415 on create and update with no changes; `application/json;
  charset=utf-8` passes. `tests/test_mcp_api.py` unchanged and green (no existing test used
  `content=`/`data=`).
- Docs: "Residual risk (REST origin check)" paragraph in `docs/ARCHITECTURE.md` (by-design command
  execution, other mutating routes not covered, missing Origin allowed, XSS not mitigated).
