# Domain Pitfalls

**Domain:** Retrofitting auth + agentic explicit memory + task state machine onto an existing single-user FastAPI/WebSocket chat app (AiAdventAgentV2, Week 3 Days 11-15)
**Researched:** 2026-09-19

## Critical Pitfalls

### Pitfall 1: Frontend talks to the Agent directly on :8001 — WS auth must be enforced there, not assumed to inherit from the UI process
**What goes wrong:** `ui/static/app.js` opens `ws://<hostname>:8001/ws/chat/{chat_id}` and issues REST calls to `AGENT_BASE = http://<hostname>:8001` **directly from the browser**, bypassing the UI process (port 8000) entirely except for serving static files. There is no reverse proxy in front of the Agent. If auth is implemented only as "login sets a cookie, browser sends it automatically," it's easy to assume the UI process (which serves the login page) is in the request path for every call and forget that the *Agent* process is the one that must independently validate the session on both its REST routes and its WS handshake.
**Why it happens:** The two-process split is easy to reason about for REST (add a dependency to `agent/main.py` routes) but WebSocket auth in Starlette/FastAPI does **not** go through the same `Depends()` machinery cleanly — `websocket.receive_json()` loop bypasses HTTP dependency injection once inside the handler, and `Depends()` on a WS route only runs once at handshake, easy to get wrong or skip.
**Consequences:** An unauthenticated (or cross-user) WebSocket connection can stream a chat's tokens even though REST is "protected," because the two code paths were secured independently and inconsistently. This is the single most common WS-auth-retrofit bug.
**Prevention:** Reuse the exact pattern already in `agent/ws.py::ws_chat` for origin validation — it validates and rejects **before** `websocket.accept()` (`if not _validate_origin(websocket): await websocket.close(code=1008, ...); return`). Add a session/cookie check in the same pre-accept position, parsing `websocket.headers.get("cookie")` manually (FastAPI `Depends()` for cookies technically works on WS routes in recent versions, but manual parsing at the same guard point as `_validate_origin` is simpler to reason about and test). Reject with `close(code=1008)` before accept if the session is missing/invalid/expired.
**Detection:** Write a test that opens a WS connection with no cookie (or an expired/forged one) and asserts the socket closes with 1008 before any `type: token` message is ever sent — mirror the existing origin-validation test pattern.
**Phase:** Auth (foundation phase, must land before Day11-15 since all later phases assume `user_id` scoping)

### Pitfall 2: Cookies are host-scoped, not port-scoped — don't over-engineer, but don't get the host string wrong either
**What goes wrong:** Two opposite mistakes are both common: (a) engineers assume a cookie set by a response from `:8000` won't be sent to `:8001` (since CORS treats different ports as different origins) and build unnecessary token-in-query-string or postMessage bridging; or (b) the cookie is set with an explicit `Domain=localhost` attribute while the browser is actually accessing the UI via `127.0.0.1`, so `window.location.hostname` (used to build `WS_BASE`/`AGENT_BASE` in `app.js`) doesn't match the cookie's host and the cookie silently never arrives at the Agent.
**Why it happens:** Cookie scoping (RFC 6265, host+path) is genuinely different from same-origin policy (scheme+host+port) that governs CORS and `fetch`/WS — this is a well-known but frequently mis-remembered distinction.
**Prevention:** Set the auth cookie with `HttpOnly`, `SameSite=Lax` (or `Strict` if the login form posts same-site), no explicit `Domain` attribute (host-only cookie, so it naturally follows whatever hostname the browser used — `localhost` or `127.0.0.1` — to both :8000 and :8001), and `Secure=False` only because this is local-first HTTP (document this explicitly as a local-only tradeoff). Do not introduce a second token-passing mechanism for WS — the existing direct-to-:8001 cookie flow works once the host string is consistent everywhere (login response, `app.js` `AGENT_BASE`/`WS_BASE`, and any `Domain=` cookie attribute).
**Detection:** Manually test login via both `http://localhost:8000` and `http://127.0.0.1:8000` and confirm chat/WS still authenticates in both cases — regressions here are easy to miss if development only ever uses one hostname.
**Phase:** Auth

### Pitfall 3: `CORSMiddleware(allow_origins=["*"])` actively breaks authenticated cross-port requests once cookies are introduced
**What goes wrong:** `agent/main.py` currently sets `allow_origins=["*"]` (flagged in `.planning/codebase/CONCERNS.md` as a pre-existing security concern). Per the Fetch/CORS spec, browsers **reject** `Access-Control-Allow-Origin: *` combined with credentialed requests (`fetch(..., {credentials: "include"})`, which is required for the session cookie to be sent cross-port from :8000-origin JS to the :8001 Agent). This isn't a theoretical risk — the browser will silently drop the cookie or block the response, and the Auth phase will appear to "randomly" fail in the browser despite working from curl/Postman.
**Why it happens:** The wildcard CORS config predates auth and was fine for a single-user, cookie-less app; introducing cookies changes the security model but the CORS config is easy to forget since it's not touched by an "add login" PR.
**Prevention:** This is exactly the fix CONCERNS.md already recommends (allowlist `http://localhost:8000`/`http://127.0.0.1:8000`) — but now it's a **hard requirement**, not a nice-to-have. Set `allow_origins` to the explicit UI origin(s) and `allow_credentials=True`.
**Detection:** Any REST call made with the browser's fetch API using the session cookie fails with a CORS error in devtools console (not a 401) — that specific failure signature (CORS error, not auth error) is the tell.
**Phase:** Auth

### Pitfall 4: The existing "Settings fallback" pattern is duplicated across 3+ call sites — adding `user_id` scoping to it is easy to do inconsistently, leaking data across users
**What goes wrong:** CONCERNS.md documents that global-vs-per-chat settings fallback logic (`chat_id.is_(None)` = global) is independently implemented in `agent/context_engine.py::get_effective_settings`, `agent/main.py::_resolve_settings`, and `agent/ws.py::_handle_chat_message`. Auth-04 requires "all existing chats/settings/memory become scoped to the owning user." If even one of these three call sites is updated to filter by `user_id` and another is missed, one user can silently read or overwrite another user's "global" settings (or, once Day11 lands, another user's memory/facts). This also raises an unresolved design question: is `chat_id IS NULL` still a single global row shared by everyone, or does "global for user X" now mean `chat_id IS NULL AND user_id = X`? If this isn't decided explicitly, whichever call site is patched first defines the behavior by accident.
**Why it happens:** Pre-existing tech debt ("brittle fallback pattern duplicated in 3 places") collides directly with a new cross-cutting concern (user scoping) that must touch all three.
**Prevention:** Before touching call sites, decide and document: global settings become **per-user global** (`chat_id IS NULL AND user_id = X`), never a single shared row. Then — as CONCERNS.md itself recommends — centralize the fallback resolver into one function in `shared/models.py` or a FastAPI dependency *as part of the Auth phase*, so `user_id` filtering is added exactly once instead of three times. Treat this as a forced refactor, not an optional cleanup.
**Detection:** Test: two users, each with different per-chat settings and no global override, both `GET /api/v1/settings` with `chat_id=None` — assert they get different (their own) global rows, not the same row or 404.
**Phase:** Auth

### Pitfall 5: "Explicit" tool-call memory silently degrades into the existing implicit facts-extraction pattern
**What goes wrong:** The codebase already has an LLM-driven "extract facts as JSON" pipeline (`agent/context_engine.py::extract_and_update_facts`, debounced, called automatically after every user message). MEM-03 explicitly requires memory saves to happen "via tool calls (not implicit/automatic classification)." It is very tempting — and would pass a shallow acceptance check — to relabel/repurpose the existing implicit extraction call as "memory," or to build a tool but have the *system* decide when to invoke it (auto-fire the tool based on heuristics) rather than genuinely letting the LLM emit the tool call as part of its own reasoning.
**Why it happens:** The implicit pattern is already built, tested (partially), and "works" — reusing it is the path of least resistance and looks superficially similar to the requirement.
**Prevention:** Keep `extract_and_update_facts` as a separate, clearly-labeled legacy mechanism (or retire it) and build MEM-03 as a genuinely distinct code path: memory-layer tool schemas (`save_to_working_memory`, `save_to_long_term_memory`, etc.) are passed to the LLM on every turn where memory-writing is relevant, and a write only happens when the model's response actually contains a `tool_calls` entry with that name — never inferred from prose ("I'll remember that...") and never auto-triggered by the backend on a timer/debounce.
**Detection:** Log every memory write with its triggering `tool_call.id`; if any write path has no corresponding tool-call id in the log, it's not "explicit" per MEM-03.
**Phase:** Day11 Memory

### Pitfall 6: The model narrates a save without actually emitting the tool call ("hallucinated compliance")
**What goes wrong:** LLMs frequently produce text like "Got it, I've saved your preference" without emitting the corresponding `tool_calls` payload, especially on smaller/local models. If the UI or downstream logic trusts the assistant's prose as evidence that memory was written, MEM-04 ("inspect what data landed in each layer") will show nothing while the chat transcript claims otherwise — a confusing, hard-to-debug demo failure.
**Why it happens:** Function/tool calling reliability varies significantly by model; local models served via LM Studio are frequently less consistent at emitting well-formed tool calls than DeepSeek's cloud API, and this app explicitly supports both backends.
**Prevention:** Treat the tool-call event (not the text) as the only source of truth for "was this saved." Consider a system-prompt instruction that forbids claiming a save happened unless the tool call is present in the same turn, and — since this app already supports switching LLM backends — explicitly test the chosen default model's tool-calling reliability with LM Studio before committing the demo to a local model; if it's unreliable, default the memory-tool-calling phases to the DeepSeek backend and document local-model tool-calling as a known limitation rather than silently failing during a graded demo.
**Detection:** Compare "assistant text claims a save" vs "a tool call with that name appears in the same response" across a test transcript; any mismatch is this pitfall.
**Phase:** Day11 Memory

### Pitfall 7: Memory/task tool-call writes racing against the existing debounced-background-task pattern
**What goes wrong:** `agent/ws.py::_handle_chat_message` holds a per-chat `asyncio.Lock` (`agent/state.py::chat_locks`) for the duration of processing one message — this is the existing, correct concurrency boundary. But `extract_and_update_facts` already runs as a **debounced background task outside that lock** (2s delay, per CONCERNS.md). If Day11/Day13 tool-call-triggered memory/task writes reuse this same "fire a background task, don't await it under the lock" pattern (e.g., to avoid blocking token streaming), a memory or task-state write can commit *after* the lock for a later message has already been released and a subsequent message's writes have landed — last-write-wins silently drops the tool-call's data. This is a direct extension of the already-documented "Debounced Facts Extraction Loses Rapid Messages" bug.
**Why it happens:** The existing codebase has one precedent for "async side-effect outside the main lock" and it's natural to copy that pattern for new side-effects, without noticing it was already flagged as lossy.
**Prevention:** Execute tool calls (memory writes, task creation/transition) **synchronously within the same per-chat lock and the same DB session/transaction** as the message that triggered them — not as a fire-and-forget background task. This also naturally fixes ordering when the LLM emits multiple tool calls in one turn (see Pitfall 8).
**Detection:** Send two rapid messages in the same chat, each triggering a distinct memory-tool-call save; assert both saves are present afterward (this mirrors the existing rapid-message facts-extraction bug and should be a regression test).
**Phase:** Day11 Memory, Day13 Task State

### Pitfall 8: Parallel/multiple tool calls in one LLM turn executed out of order or concurrently, corrupting task/memory state
**What goes wrong:** OpenAI-compatible APIs (DeepSeek included) can return multiple `tool_calls` in a single response (e.g., `save_to_memory` + `create_task` + `transition_task_state` all in one turn). If these are executed concurrently (e.g., `asyncio.gather`) or in the order returned without checking dependencies, a `transition_task_state` call can race with the `create_task` call it depends on (referencing a task ID that doesn't exist yet in the DB), or two state-mutating tool calls can interleave their DB writes unpredictably.
**Why it happens:** It's tempting to execute independent-looking tool calls concurrently for latency, but "independent-looking" is a modeling assumption the LLM's own multi-call turn may violate.
**Prevention:** Execute tool calls from a single assistant turn **strictly sequentially, in the order the model returned them**, within the same transaction/lock as Pitfall 7. Never `asyncio.gather` tool-call execution for this app's memory/task tools. Return each tool's real result (including generated IDs) so a later call in the same turn that depends on it gets the correct value.
**Detection:** Test a turn with two tool calls where the second references the first's output ID; assert the second succeeds and doesn't see a stale/missing ID.
**Phase:** Day11 Memory, Day13 Task State

### Pitfall 9: Tool-call side effects survive even when the overall turn is later rolled back / the user message is deleted
**What goes wrong:** CONCERNS.md documents that on context overflow (`no_compression` strategy) or a mid-stream LLM failure, the just-submitted user message is deleted and the client sees `CONTEXT_OVERFLOW` or an error with no reply. If a tool call already executed and committed a memory write or task-state transition *before* the failure/overflow was detected (tool calls can happen before the final assistant text is fully streamed), that memory/task write survives even though, from the user's perspective, "the message failed" and they'll likely resend it — potentially causing a duplicate or orphaned memory entry that references a deleted message.
**Why it happens:** This app's existing error-handling pattern treats "delete the user message" as the recovery action for stream failures; that pattern predates any tool-call side effects and doesn't account for them.
**Prevention:** Either (a) make memory/task-state tool-call writes soft-nullable/reversible by tagging them with the triggering message ID, so a message deletion can cascade-clean or flag orphaned memory/task rows, or (b) defer tool-call execution/commit until after the full assistant turn (including overflow checks) has succeeded. Option (a) is more consistent with this app's "database always keeps full history" philosophy; whichever is chosen, decide explicitly rather than leaving orphaned rows as an accidental side effect.
**Detection:** Trigger a context overflow after a turn that includes a memory-saving tool call; check whether the memory row persists with no corresponding message in the tree.
**Phase:** Day11 Memory, Day13 Task State

### Pitfall 10: FSM "soft enforcement" (prompt-only) window between Day13 (tasks) and Day15 (hard transition checks)
**What goes wrong:** Per PROJECT.md, task states (`planning → execution → validation → done`) and creation land in Day13, but the *hard* transition-validation check (TRANS-01/02) is a separate, later phase (Day15). By course design, Day13 and Day14 will have tasks whose transitions are enforced only by system-prompt instructions — the LLM can and will occasionally skip states (e.g., jump straight to `done`) or invent invalid transitions during that window, and any data/UI built during Day13-14 (task history, "current task" display) will contain these illegal transitions once Day15's hard check is retrofitted.
**Why it happens:** This is an intentional, sequenced course structure, but it's exactly the kind of soft-then-hard enforcement gap that's easy to forget once Day13 "looks done" — the temptation is to treat Day13's prompt-based FSM as sufficient and skip stress-testing illegal transitions until Day15.
**Prevention:** Store the full transition **history** (not just current state) from Day13 onward specifically so Day15's hard check has something to validate against retroactively, and explicitly test illegal-transition attempts during Day13/14 (expect them to currently *succeed* incorrectly) as a baseline, then re-run the same test after Day15 lands and expect rejection. Don't design Day13's task table schema in a way that assumes transitions were always legal (e.g., don't skip storing a `from_state`/`to_state`/`rejected` audit log).
**Detection:** A test suite that attempts `planning → done` directly: expected to succeed (undesirably) before Day15, expected to be rejected with a clear error after Day15 — track this test's expected result changing across phases as a deliberate signal.
**Phase:** Day13 Task State (schema/audit-log groundwork), Day15 Controlled Transitions (hard enforcement)

## Moderate Pitfalls

### Pitfall 1: Hard invariant/transition checks that only inspect tool-call arguments miss prose-based violations
**What goes wrong:** INV-04 says a dedicated check inspects "the agent's response/tool calls" for conflicts. If the implementation only validates structured tool-call arguments (e.g., checking `transition_task_state(new_state=...)` against the allowed-transitions graph) but never scans the assistant's free-text response, the model can still describe or perform a forbidden action in prose without a matching tool call, and the "hard" check won't catch it.
**Prevention:** Decide explicitly whether the conflict check scans prose text too (harder, needs a second LLM-judge call or a keyword/pattern check) or is scoped only to tool-call arguments (simpler, cheaper, but narrower guarantee) — and document the scope as a known limitation rather than implying blanket coverage. For a course-scope project, scoping to tool-call arguments only is reasonable, but say so explicitly in INV-04's acceptance criteria.
**Prevention strategy:** State the scope in the phase's spec before implementation, not after a demo reveals the gap.
**Phase:** Day14 Invariants

### Pitfall 2: Global vs per-chat invariant precedence is undefined, causing non-deterministic prompt behavior
**What goes wrong:** INV-01/02 allow per-chat invariants layered on global ones. If a per-chat invariant contradicts a global one (e.g., global "respond in English" vs. per-chat "respond in Russian for this chat"), simply concatenating both into the system prompt leaves resolution to the model's own recency/position bias, which is inconsistent across models and prompt lengths.
**Prevention:** Define an explicit precedence rule (e.g., "per-chat invariants override global on direct conflict, both are always injected, per-chat is listed closer to the user turn") and state it in the injected prompt itself ("if a per-chat rule conflicts with a global rule, the per-chat rule wins"), rather than relying on implicit prompt-position effects.
**Phase:** Day14 Invariants

### Pitfall 3: Pause/resume relies on compressed chat history instead of the working-memory table as source of truth
**What goes wrong:** TASK-04 requires resuming a paused task "without re-explaining context." If resume logic re-derives task context by re-reading the chat's message history through the active compression strategy (`sliding` keeps only the last 10 messages; `sticky`/`truncate_middle` summarize/drop older ones), the very messages that established the task's working data may already have been compressed away or summarized lossily by the time of resume — especially for a task paused for a long time in a busy chat.
**Prevention:** Working memory (the dedicated SQLite table per MEM-02) must be the authoritative source for resume, independent of whatever the current context-compression strategy would reconstruct from raw dialog. On resume, inject the task's working-memory row directly into context rather than relying on the compressed message history to "still contain" it.
**Phase:** Day13 Task State, Day15 Controlled Transitions (resume-from-pause specifically)

### Pitfall 4: Unbounded long-term memory growth mirrors the already-flagged unbounded `facts_json` growth
**What goes wrong:** CONCERNS.md already flags `Settings.facts_json` as an unbounded TEXT field. A new dedicated long-term-memory table (MEM-02) without a size/count cap or pruning strategy will hit the same problem, compounded because tool-call-driven saves are more frequent/eager than the existing debounced extraction, and because every save is also injected back into context (PERS-02-style), growing the system prompt over time and eventually contributing to the exact context-overflow bug already documented for `no_compression`.
**Prevention:** Cap long-term memory entries (count and/or total character budget) per user from day one; decide what happens on overflow (oldest-evicted? explicit prompt injection warns the LLM it's near capacity?) rather than letting it grow silently until it inflates every subsequent turn's token count.
**Phase:** Day11 Memory

### Pitfall 5: Memory-poisoning via injected content the LLM treats as a "successful" fact to remember
**What goes wrong:** If long-term memory content is ever influenced by untrusted external content (pasted text, fetched URLs, file uploads — even if not in this milestone's explicit scope, likely to appear later), an attacker can craft content that causes the LLM to "helpfully" call the save-to-memory tool with attacker-controlled instructions, which then get re-injected into every future turn's system prompt as if they were the user's own established facts/preferences. This is distinct from ordinary same-session prompt injection because it persists indefinitely across sessions.
**Prevention:** Even though this milestone is single-source (chat only, no external content ingestion), design the memory schema and injection path now so that a future "read a URL/file" tool doesn't get a free pass to write to long-term memory — e.g., tag memory entries with a provenance/trust field, or require the memory-write tool calls to only be reachable from genuine user-turn context, not from tool-result content that itself could contain instructions.
**Phase:** Day11 Memory (design-time consideration), flag for future phases if external content ingestion is ever added

## Minor Pitfalls

### Pitfall 1: Login endpoint has no brute-force protection
**What goes wrong:** CONCERNS.md already notes REST endpoints have no rate limiting. A login endpoint is the highest-value target for this gap — trivial to brute-force a weak password with no lockout/backoff.
**Prevention:** Add basic per-IP or per-username rate limiting/lockout specifically on the login route, even if general REST rate limiting remains deferred elsewhere.
**Phase:** Auth

### Pitfall 2: Password hashing scheme not specified
**What goes wrong:** Given the app previously had zero auth, it's easy to reach for a quick `hashlib.sha256` "good enough for a course project" implementation.
**Prevention:** Use `passlib`/`bcrypt` or `argon2-cffi` with a per-user salt (both are effectively drop-in with FastAPI); don't hand-roll hashing even for coursework, since the habit matters more than the specific grading rubric.
**Phase:** Auth

### Pitfall 3: `"null"` origin allowance interacts oddly with auth
**What goes wrong:** `_validate_origin()` already allows `origin == "null"` (documented as low risk in CONCERNS.md for the single-user case). Once auth exists, a malicious local `file://` page could still open a WS connection if it can also obtain a valid session cookie by some other means (e.g., XSS elsewhere) — the origin check alone was never a strong boundary, but it's easy to mistake it for one once "real" auth exists.
**Prevention:** Treat session-cookie validation as the actual security boundary; origin validation remains a defense-in-depth layer only. Don't let the presence of auth cause the `"null"` origin allowance to be forgotten/reconsidered — flag it explicitly during Auth phase review.
**Phase:** Auth

## Phase-Specific Warnings

| Phase Topic | Likely Pitfall | Mitigation |
|-------------|---------------|------------|
| Auth | WS auth checked in a different place/way than REST auth, creating an inconsistent boundary | Reuse the existing pre-accept `_validate_origin`-style guard in `agent/ws.py::ws_chat` for session validation too |
| Auth | `CORSMiddleware(allow_origins=["*"])` blocks credentialed cross-port cookie flow | Fix to an explicit origin allowlist + `allow_credentials=True` as part of this phase, not deferred |
| Auth | Settings/global-vs-per-chat fallback duplicated in 3 call sites, inconsistently updated for `user_id` | Centralize the resolver as part of this phase (forced refactor) |
| Day11 Memory | Tool-call memory writes racing the existing debounced-background-task pattern (facts extraction precedent) | Execute tool calls synchronously inside the per-chat lock/transaction, not as fire-and-forget background tasks |
| Day11 Memory | "Explicit" memory quietly becomes a relabeled version of the existing implicit `extract_and_update_facts` | Build a genuinely separate tool-call code path; log every write with its triggering `tool_call.id` |
| Day11 Memory | Local LM Studio model unreliable at emitting tool calls, undermining MEM-03 in a live demo | Verify tool-calling reliability on the actual configured model before committing; default to DeepSeek if needed |
| Day12 Personalization | Profile injected into every request risks growing the system prompt unboundedly alongside long-term memory | Cap profile/preference content size; treat as part of the same token-budget accounting as memory |
| Day13 Task State | Multiple tool calls in one LLM turn (create + transition) executed out of order or concurrently | Execute sequentially in returned order, within one transaction; never `asyncio.gather` tool execution |
| Day13 Task State | Resume-from-pause relies on compressed chat history instead of the working-memory table | Treat working memory as authoritative source of truth for resume, independent of active compression strategy |
| Day14 Invariants | Hard conflict check only inspects tool-call args, silently missing prose-based violations | Explicitly scope and document what the check covers |
| Day14 Invariants | Global vs per-chat invariant conflicts resolved only by prompt position (non-deterministic) | Define and state an explicit precedence rule in the injected prompt |
| Day15 Controlled Transitions | Illegal transitions already happened during the Day13-14 soft-enforcement window; no audit trail to reconcile | Store transition history with `from_state`/`to_state` from Day13 onward, not just current state |
