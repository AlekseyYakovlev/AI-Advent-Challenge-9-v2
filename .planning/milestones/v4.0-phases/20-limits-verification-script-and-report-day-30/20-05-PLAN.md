<!-- HTTP contract of the Agent that the script uses (all routes accept `Authorization: Bearer <key>` unless stated) -->
| Step | Call | Expected |
|------|------|----------|
| Reachability | `GET {url}/health` without credentials | 200 |
| Auth, good key | `GET {url}/api/v1/auth/me` | 200 `{"id": int, "username": str}` |
| Auth, wrong key | the same call with a deliberately invalid key | 401 |
| Models | `GET {url}/api/v1/llm-providers/models` | 200 list of groups `{"provider_id": int, "name": str, "kind": str, "models": [{"id": str, "loaded": bool or null}], "error": str or null}` |
| Create chat | `POST {url}/api/v1/chats` body `{"title": str}` (title up to 200 characters) | 200 or 201 `{"id": int, "title": str, ...}` |
| Per-chat settings | `PUT {url}/api/v1/settings` body `{"chat_id": int, "strategy": "no_compression", "context_length": 512, "max_tokens": 256}` (512 and 256 are the schema minimums; `system_prompt` is also accepted) | 200 |
| Chat turn | `POST {url}/api/v1/chats/{id}/messages` body `{"content": str, "model": str, "provider_id": int}` (content up to 100000 characters) | 200 `{"content": str, "stats": {..., "queue_wait_seconds": float}, ...}`; errors have the body `{"detail": str, "code": str, ...}` |
| Chat turn, limit exceeded | same | 429, header `Retry-After: <int>`, body code `RATE_LIMITED`, `retry_after` |
| Chat turn, overflow | same, on a chat with strategy `no_compression` and `context_length` 512 and a long message | 413, body code `CONTEXT_OVERFLOW`, `suggested_strategy` |
| Delete chat | `DELETE {url}/api/v1/chats/{id}` | 204 with an empty body |

Facts that shape the design:
- The limit is per chat; parallel requests into one chat would answer 409 `CHAT_BUSY`, so each parallel request gets its own chat
- A turn that fails with 413 still takes a slot in the chat's rate window, and the 413 is produced before the model is called (a valid `model` and `provider_id` are still required)
- The server exposes no route with its limit values (D-06), so the script cannot read them; the operator may pass them as information-only flags
- A request without an `Origin` header passes the server's Origin check; the script never sends one
- With the server's generation cap of 2 and N greater than 2, some parallel requests wait in the server's queue; the wait is in `stats.queue_wait_seconds`
