    `LoginThrottle` (D-07, D-08): private dataclass `_Entry` with `failures: int`, `last_failure: float`, `blocked_until: float` (`0.0` means no block was applied); `self._entries: dict[tuple[str, str], _Entry]`. The key is `(username, client_ip)` and the class treats it as opaque. D-08 is followed literally: "consecutive" means "with no successful login in between", so the failures of a key are kept until `reset(key)` or until the block they caused has expired, and they are never forgotten because of their age. `blocked_seconds(key)`: return None when `settings.LOGIN_MAX_FAILED_ATTEMPTS <= 0` or there is no entry; when `blocked_until - _now() > 0` return `max(1, math.ceil(remaining))`; when a block was applied and has expired (`0 < blocked_until <= now`), delete the entry (the count starts from zero after a block) and return None; an entry without a block is left untouched whatever its age. `record_failure(key)`: return False at once when the threshold is `<= 0`; if the key's entry holds an expired block, discard that entry first; otherwise keep the existing count however old `last_failure` is; increment `failures`, set `last_failure = now`; when `failures >= threshold` set `blocked_until = now + settings.LOGIN_LOCKOUT_SECONDS` and remember that a block started; then run the eviction described below; return whether a block started. `reset(key)` pops the entry (a successful login resets the counter, D-08). `clear()` empties the dict. The class logs nothing: the login route in plan 20-03 logs with the username and IP it knows.

    Eviction (the memory bound; it runs at the end of every `record_failure`, in this order). Step 1: remove every entry whose block has expired; this loses nothing, because it is the state `blocked_seconds` would produce for that key. Step 2: while `len(self._entries) > self.MAX_ENTRIES`, remove the entry that is not currently blocked and has the oldest `last_failure`, never the key that was just recorded; only if every other entry is currently blocked, remove the one whose `blocked_until` is earliest. Write the consequence as a comment above the method (plan 20-07 repeats it in the docs): a pair evicted in step 2 loses its failure count and starts again from zero, which happens once more than `MAX_ENTRIES` (10,000) different username+address pairs hold failures at the same time. This is not expensive to cause: failed logins under unknown usernames are fast because they skip password hashing, so a client already on the LAN can flood them and push its own counter out of the table after every few guesses. The lockout therefore slows casual guessing but does not stop a determined attacker on the LAN (accepted, T-20-01 and T-20-60 of plan 20-03). An active block is evicted only when more than `MAX_ENTRIES` pairs are blocked at once.

    `GenerationGate` (D-12, D-13): attributes `_semaphore: asyncio.Semaphore | None`, `_cap: int`, `_loop: asyncio.AbstractEventLoop | None`, `_waiting: int` (starts at 0). Private `_current()` reads `settings.MAX_CONCURRENT_GENERATIONS` at call time; returns None when it is `<= 0`; otherwise returns the stored semaphore, creating a new `asyncio.Semaphore(cap)` whenever none exists, the cap differs from `_cap`, or `asyncio.get_running_loop()` is not `_loop` (a module-level semaphore created once would break across the per-test event loops). The read-only property `waiting` (`def waiting(self) -> int` under `@property`) returns `_waiting`: the number of callers that found no free slot and have not got one yet. `slot(on_wait=None)` is an `@asynccontextmanager` that yields a `float`: with no semaphore yield `0.0`; otherwise hold the semaphore in a local variable; when it is not locked acquire immediately with a wait of exactly `0.0`; when `semaphore.locked()` is true, take `started = _now()` first, then increment `_waiting`, and inside a `try` call `await on_wait()` once if given and then `await semaphore.acquire()`, with `_waiting` decremented in the `finally` of that `try` (the count drops when the waiter gets its slot, when it is cancelled and when `on_wait` raises); the wait is `_now() - started` rounded to 3 decimals. The start time is taken before the count is raised on purpose: a test that observes `waiting == N` and then advances a patched clock knows the advance is included in every waiter's result. Acquiring the slot happens before the `try` that guards the body; the `yield` sits in that `try` and the release in its `finally` on the same local semaphore object, so a caller cancelled while waiting holds nothing and a body that raises still frees its slot. There is no timeout and no length limit anywhere in the gate (D-13: a queued turn always runs). `reset()` forgets the semaphore and the loop and sets `_waiting` to 0.
