<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Authenticated browser → `POST /api/v1/auth/users` | Attacker-controlled username and password strings cross into a password-hashing and unique-index write path. |
| New account → existing users' data | A freshly minted identity immediately exercises the `user_id` scoping built in Plans 02-04. |
| API error `detail` → DOM (`#add-user-error`) | Server-supplied text is rendered into the page. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-01-30 | Elevation of Privilege | Unauthenticated account creation (an accidental public signup route) | mitigate | **HIGH.** The route depends on `get_current_user`; Task 1 asserts an unauthenticated POST returns 401 and writes no row. D-06 forbids any alternate unauthenticated path, and no second route is added. |
| T-01-31 | Information Disclosure | `password_hash` leaking in the creation response | mitigate | `response_model=UserResponse`, which carries only `id` and `username`; a test asserts the key is absent from the JSON rather than trusting the model. |
| T-01-32 | Spoofing | Account takeover by re-registering an existing username and overwriting its hash | mitigate | Pre-check plus the DB unique index; duplicates raise 409 and NEVER update the existing row. The `IntegrityError` branch covers the check-then-insert race, so a concurrent duplicate is a 409, not a 500 or an overwrite. |
| T-01-33 | Information Disclosure | Username enumeration through the duplicate-username 409 | accept | Deliberate and required: the UI must tell the creator why the name was rejected (UI-SPEC Copywriting Contract). Unlike the login endpoint (T-01-02), this path already requires a valid session, so the disclosure is to a trusted, authenticated user of a single-machine, local-only app. |
| T-01-34 | Tampering | XSS through the API `detail` string rendered into `#add-user-error` | mitigate | The error is written with `textContent` semantics only — never `innerHTML`, never a `DOMPurify`-less HTML insert, per CLAUDE.md's frontend rule. `showToast` already uses `textContent`; the inline error slot must do the same. |
| T-01-35 | Elevation of Privilege | Weak passwords on accounts created by this route | accept | Same disposition as T-01-09: D-12 explicitly accepts any non-empty password, enforced as `min_length=1` on both the API schema and the form. Deliberate, documented user decision. |
| T-01-36 | Information Disclosure | A new account inheriting or seeing its creator's chats/settings | mitigate | No data is copied at creation; every read path filters on `user_id` (Plans 03/04). Task 1 asserts the new account gets `[]` from `GET /api/v1/chats` and 404 on the creator's chat id. |
</threat_model>
