<objective>
Give every existing row an owner. Create the bootstrap admin account on first run (D-05), print its credentials exactly once where the developer will actually see them (`run.py`'s stdout, not the Agent's redirected log file), add nullable `user_id` FK columns to `chat` and `settings`, and backfill every pre-existing row to that bootstrap admin (D-07).

Purpose: The app already has real chats and settings on disk. Without this slice, turning on auth in Plan 03 would make the existing user's entire history invisible. This is the data-continuity half of the Walking Skeleton's "one real DB read/write".

Output: `migrate_add_user_id_columns()`, `ensure_bootstrap_admin()`, `backfill_user_id()`, `bootstrap_admin_if_needed()`, the `Chat.user_id` / `Settings.user_id` columns, and a visible first-run credential banner.
</objective>

    In `shared/models.py`, add to `Chat` and to `Settings` a field `user_id: Optional[int]` declared with `default=None` and `sa_column=Column(Integer, ForeignKey("user.id", ondelete="CASCADE"), nullable=True)`. It MUST be nullable — see the migration constraint below. Never `Field(ondelete=...)`. CASCADE is deliberate: deleting a user removes their chats and settings, which is the ownership semantics AUTH-04 asks for.

    In `shared/database.py` add `async def migrate_add_user_id_columns(conn: Any) -> None`, mirroring `migrate_add_context_length` exactly — for each of the table names `chat` and `settings`: a `SELECT name FROM sqlite_master WHERE type='table' AND name=<table>` existence check that `continue`s when the table is absent, a `PRAGMA table_info(<table>)` read of existing column names, and an `ALTER TABLE <table> ADD COLUMN user_id INTEGER REFERENCES user(id)` only when `user_id` is missing, with `logger.info("migrating_add_user_id", table=table)` before it.
    CRITICAL: no `NOT NULL` on that ALTER. SQLite refuses `ADD COLUMN` with `NOT NULL` when the column carries a `REFERENCES` clause and `PRAGMA foreign_keys=ON` is active (which `_set_sqlite_pragma` sets on every connection). Non-nullness is enforced at the application layer in Plan 03, not at the schema level. Do not attempt the 12-step table rebuild — explicitly out of scope.

    Add `async def ensure_bootstrap_admin() -> tuple[str, str] | None`: open an `async_session_factory()` session, `select(User)` and return `None` if any row exists; otherwise generate `username = "admin"` and `password = secrets.token_urlsafe(18)`, insert `User(username=username, password_hash=hash_password(password))` using the `try: await session.commit(); await session.refresh(row) / except Exception: await session.rollback(); raise` convention, `logger.info("bootstrap_admin_created", username=username)` — never logging the password — and return `(username, password)`.

    Add `async def backfill_user_id(admin_id: int) -> None`: inside `engine.begin()`, execute `UPDATE chat SET user_id = :admin_id WHERE user_id IS NULL` and the same for `settings`, both parameter-bound (never f-string-interpolated), logging `logger.info("backfilled_user_id", table=..., rows=result.rowcount)`. The `WHERE user_id IS NULL` clause is what makes it non-destructive to already-owned rows.

    Add `async def bootstrap_admin_if_needed() -> tuple[str, str] | None`: `await init_db()`, then `credentials = await ensure_bootstrap_admin()`, then resolve the admin id — if credentials were just created use that user, otherwise select the oldest `User` row by `created_at` ascending as the owner of legacy data (D-07: one migration path, no separate legacy-user concept) — then `await backfill_user_id(admin_id)` and return `credentials`. If there is no user at all, return `None` without backfilling.

    Extend `init_db()` to call `await migrate_add_user_id_columns(conn)` before `conn.run_sync(SQLModel.metadata.create_all)`, keeping `migrate_add_context_length` and `_migrate_legacy_strategies` in their current positions. Confirm `User` and `Session` are reachable from `SQLModel.metadata` (they are imported via the `from shared.models import ...  # noqa: F401` line — extend that list rather than adding a new import statement).

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Terminal stdout ← `run.py` | The bootstrap password crosses into a human-readable channel exactly once. |
| Migration code → existing `app.db` | Untrusted-by-age pre-auth rows get assigned an owner. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-01-10 | Elevation of Privilege | Bootstrap admin with a predictable password | mitigate | Password is `secrets.token_urlsafe(18)` (~144 bits), generated per install; never a fixed literal like `admin`/`changeme`. A test asserts the value is not a short fixed default. |
| T-01-11 | Information Disclosure | Bootstrap password leaking into `logs/agent.log` or structlog output | mitigate | The password is emitted only via `print()` in `run.py`. `ensure_bootstrap_admin` logs `bootstrap_admin_created` with the username only. An acceptance criterion greps for any logger line carrying `password` in both files. |
| T-01-12 | Tampering | SQL injection through the backfill statement | mitigate | `backfill_user_id` binds `:admin_id` as a parameter; the only interpolated tokens are the two hardcoded table-name literals `chat` and `settings`, never user input. |
| T-01-13 | Denial of Service | A failed/partial migration bricking an existing `app.db` | mitigate | The migration is purely additive (`ADD COLUMN`, `UPDATE ... WHERE user_id IS NULL`), guarded by `sqlite_master` and `PRAGMA table_info` existence checks, and proven re-runnable by an idempotency test. No `DROP`, no table rebuild, no data deletion. |
| T-01-14 | Repudiation | Legacy rows with no traceable owner | mitigate | `backfill_user_id` leaves zero NULL `user_id` values, asserted by test; D-07's single-migration-path (bootstrap admin owns everything pre-auth) avoids an ambiguous "orphan" state. |
| T-01-15 | Elevation of Privilege | Schema-level `user_id` nullability permitting an unowned row later | accept | SQLite cannot add a `NOT NULL` FK column via `ALTER TABLE ADD COLUMN`; the 12-step table rebuild is out of scope for this slice. Non-nullness is enforced at the application layer in Plan 03 (every insert sets `user_id` from `current_user`) and every read filters on it, so an unowned row is unreachable through the API. |
</threat_model>
