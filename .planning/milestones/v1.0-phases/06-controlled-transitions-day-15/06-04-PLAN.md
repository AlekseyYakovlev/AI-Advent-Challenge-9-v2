  <name>Task 2: Day 15 acceptance demo — illegal transition, explained rejection, resume</name>
  <what-built>
Phase 6 is complete across three plans: a server-side transition graph (`planning → execution → validation → done`, one-step-back rework, hard terminal states) enforced in `agent/tasks.py`; refused attempts persisted as `rejected=True` rows in the shared task history; rejections promoted to `ok=False` so the WebSocket fires a `TOOL_ERROR` frame unconditionally; a justify-or-retract re-prompt after an illegal transition; HTTP 409 on manual pause/resume/cancel when the graph forbids them; and refused attempts rendered inline, red and struck through, in the Tasks tab timeline.
  </what-built>
  <how-to-verify>
Start the app with `python run.py` and open http://localhost:8000 in Chrome, then log in.

1. **Illegal transition is rejected (TRANS-01, criterion 1).** In a new chat, ask the agent to create a task (e.g. "заведи задачу: подготовить отчёт"). Confirm the task appears in the Tasks tab in state `планирование`. Then ask the agent to mark it done immediately (e.g. "отметь задачу #N как выполненную"). Expected: the task stays in `планирование` — it does NOT jump to `готово`.

2. **Rejection is clear and explainable (TRANS-02, criterion 2).** During that same turn, expect a red error toast carrying the rejection reason (which task, which state it is in, which states are legal next), and expect the assistant to follow up in chat either proposing the legal next step (`выполнение`) or explaining why it tried. Confirm nothing crashed: no blank reply, no disconnected socket, and the chat remains usable afterwards.

3. **Refused attempt is visible in the timeline (D-11).** Open the Tasks tab and expand that task's history. Expected: a red, struck-through row reading like `попытка → готово: отклонено (…)` sitting inline, in chronological order, among the normal transition rows.

4. **Manual controls respect the graph (D-03/D-04).** Walk the task through the legal path by asking the agent to move it to `выполнение`, then `проверка`, then `готово`. Now click Cancel on that finished task — expected: an error toast, and the task stays `готово`. Click Resume on a task that is not paused — expected: an error toast, no state change.

5. **Resume continues along the graph with working memory intact (TRANS-03, criterion 3).** Create a second task, let the agent write something into working memory for it, then pause it. Send at least a dozen unrelated messages so the conversation grows past the sliding window. Resume the task and ask the agent what that task's state and next step are. Expected: the agent still knows the task, its state, and the working-memory content, and any state change it makes is a single legal step.

Note the known pre-existing quirk (explicitly out of scope, do not report as a bug): the typing indicator may disappear when the error toast fires while more assistant text is still streaming in.
