<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Task rows → LLM system prompt | LLM-authored task titles/descriptions/goals are re-injected into a privileged position in every subsequent prompt |
| Chat scope → prompt assembly | `build_system_prompt` must read only the current chat's tasks |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-04-22 | Information Disclosure | `build_system_prompt` open-task block | mitigate | `list_open_tasks` filters strictly on `Task.chat_id == chat_id`, so one chat's tasks can never leak into another chat's prompt. Covered by `test_task_injection_is_scoped_to_the_chat`. |
| T-04-23 | Denial of Service (self-inflicted) | unbounded prompt growth from the task block | mitigate | The block excludes `done` and `cancelled` tasks, giving it a natural ceiling that `WorkingMemory`/`LongTermMemory` lack; combined with the Pydantic length caps from 04-01 (title 200 / description 5 000 / goal 2 000), the per-task contribution is bounded. Under the `no_compression` strategy an oversized context still raises the existing `ContextOverflowError` rather than silently truncating. |
| T-04-24 | Tampering | Prompt injection via LLM-authored task text | accept | A task title/goal is written by the same model that reads it back, inside the same user's own chat — there is no cross-principal escalation path, and the block is clearly delimited by the `Open tasks in this chat:` header. Length caps bound the blast radius. Revisit in Phase 5 if invariant conflict-checking needs to reason about injected task text. |
| T-04-25 | Tampering | Divergent context-assembly paths | mitigate | The injection is added inside `build_system_prompt` only; `grep -cE "list_open_tasks\|list_tasks_for_chat" agent/ws.py` must return 0, preventing the duplicate-token-accounting anti-pattern flagged in RESEARCH §Don't Hand-Roll. |
| T-04-SC | Tampering | npm/pip/cargo installs | accept | No new packages in this phase; `requirements.txt` unchanged. |
</threat_model>
