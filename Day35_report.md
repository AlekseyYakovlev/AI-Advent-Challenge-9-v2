# Day 35 — AI-пайплайн релиза: отчёт

## Задание

Задание дня 35: полностью автоматизировать подготовку релиза этого репозитория — собрать изменения, написать changelog, выбрать версию, поставить тег и создать черновик GitHub Release (D-01, D-02). Результат сдаётся видео и кодом, ветка `Day35`.

Что построено в этой фазе:

- Команда `/release` в чате: читает репозиторий через MCP, строит план релиза, ждёт явного подтверждения и выполняет четыре шага записи.
- Модули `agent/release_pipeline.py` (чистая логика: фильтр коммитов, разбор ответов, сообщение тега), `agent/release_planner.py`, `agent/release_executor.py`, `agent/release_llm.py`, `agent/release_mcp.py`, `agent/release_handler.py`, `agent/release_command.py`.
- Расширение встроенного git-сервера `mcp_servers/project_git.py` (флаг `--allow-release`): инструменты `release_context`, `release_range_commits`, `release_commit_changelog`, `release_create_tag`, `release_push`, `github_create_draft_release`.
- Карточка плана релиза и результата во фронтенде, скрипт `scripts/e2e_release_playwright.py` с четырьмя контрольными сценариями.

## Как устроен пайплайн

1. Пользователь пишет `/release` (или `/release <диапазон>`).
2. Приложение читает репозиторий через MCP-инструменты; каждый вызов показан карточкой инструмента.
3. Код фильтрует коммиты (служебные, только `.planning/`, merge без смысла) и считает, сколько отброшено (D-07).
4. ИИ пишет текст changelog по сгруппированным коммитам (D-08).
5. Код строит кандидатов версии; ИИ выбирает один из них и пишет название и обоснование (D-11..D-14).
6. В чате появляется карточка плана: диапазон, версия, название, changelog, шаги.
7. Пользователь явно подтверждает кнопкой «Подтвердить релиз» (D-02).
8. Выполняются четыре шага через MCP: коммит `CHANGELOG.md`, аннотированный тег, push ветки и тега, черновик GitHub Release (D-04).
9. Для каждого шага показан результат; повтор пропускает уже выполненные шаги (D-05).

| Где участвует ИИ | Где решает код |
|---|---|
| Текст changelog | Чтение истории, фильтрация коммитов |
| Выбор одной версии из двух-трёх кандидатов | Построение списка кандидатов и проверка, что версия больше последнего тега и тег свободен |
| Название и обоснование релиза | Сообщение тега (`tag_message`), порядок и выполнение шагов |
| | Блокировки: грязное дерево, смена HEAD, занятый тег |
| | Проверка changelog: допустимые заголовки, покрытие фаз и DayNN (D-17) |

ИИ ничего не пишет в репозиторий сам: он только возвращает текст, а запись выполняют инструменты после подтверждения.

## Допущение о сообщении тега (A1)

Правило реализовано в `agent/release_pipeline.py::tag_message` (D-14):

- мажорный релиз: `vX.0 Week N: <название>`, где `N = X + 2`. Смещение выведено из существующих тегов (v1.0 → Week 3 … v4.0 → Week 6);
- минорный релиз: `vX.Y: <название>` без «Week».

Минорная форма без «Week» — **допущение**, пользователь её не подтверждал (RESEARCH A1). Если нужен другой формат, он меняется в этой одной функции.

## Отступление от D-04

D-04 предполагал создание Release через github-mcp-server. Версия v2.0.2 не содержит инструмента создания релиза (проверено на бинарнике: 91 инструмент при `--toolsets=all`). Поэтому черновик Release создаётся собственным узким инструментом `github_create_draft_release` в `mcp_servers/project_git.py`, включаемым флагом `--allow-release` (D-20). Это по-прежнему MCP-вызов, он показывается карточкой инструмента. Release всегда создаётся как черновик, публикации нет.

Из-за этого инструмент живёт на сервере `release-git`, а не на отдельном сервере `github`. В ходе контрольных прогонов выяснилось, что исполнитель отправлял шаг Release на несуществующий сервер `github`; это исправлено (см. «Что нашли при контрольных прогонах»).

## Безопасность

- Нет force push, push только с явными refspec (`refs/heads/<ветка>` и `refs/tags/<тег>`).
- Коммит затрагивает только `CHANGELOG.md`; если в индексе что-то ещё, шаг отказывает.
- Строго чистое дерево, включая неотслеживаемые файлы (D-21); перед записью проверяется, что HEAD не изменился с момента построения плана.
- Токен GitHub хранится только в окружении MCP-сервера, в чат и логи не попадает.
- Release всегда черновик.

## Что нашли при контрольных прогонах

Контрольные прогоны выявили четыре проблемы; первые две — в коде приложения, остальные — в скрипте. Прогоны, на которых они проявлялись, были неуспешными.

1. **Шаг Release уходил на несуществующий сервер `github`** (исправлено в `agent/release_executor.py`, добавлен регрессионный тест). Симптом: сценарий 2 давал `release: failed` с причиной «MCP server 'github' is not configured», хотя токен был задан.
2. **Нулевой ответ рассуждающей модели.** `qwen/qwen3.5-9b` тратит на рассуждения около 6000 токенов, а лимит changelog был 1800: ответ приходил пустым (`finish_reason=length`, `reasoning_tokens=1799`), сервер отвечал «Не удалось получить черновик от модели». Проверено отдельным замером: при лимитах 1800 и 4000 — 0 из 3–5 успешных ответов, при 8000 — 3 из 3 за 60–70 с. Лимиты подняты до 8192 (changelog) и 4096 (решение о версии) в `agent/release_llm.py`. Это снижает риск, но не исключает его: модель по-прежнему может не уложиться в лимит на других данных.
3. Скрипт ждал кадр `notice`, а сервер отправляет `help_notice`: быстрые уведомления не замечались и скрипт ждал весь таймаут.
4. Фикстура и подготовка песочницы: конфликт merge при создании тестовой истории, коммиты лежали только в `.planning/` и отфильтровывались как служебные, ранний выход из сценария 2 оставлял сценарии 1 и 4 без токена.

## Качество changelog

Проверка кодом (D-17): во всех шести построенных планах заголовки допустимы, пропущенных фаз и DayNN нет. Вывод: форма и покрытие в порядке. Комментарий по содержанию (по захваченным текстам):

- Модель ничего не пропустила, но писала формулировки вроде «добавлен альфа», «добавлен гамма» — склонение и смысл страдают, она пересказывает тему коммита.
- В сценарии 1 модель **выдумала** «Day01» («Фаза 92: добавлен гамма (Day01)»): такого обозначения в коммите нет, коммит назывался `feat(92-01)`.
- Слияние `Day90` модель в разных прогонах относила то к «Добавлено», то к «Изменено»: классификация нестабильна.
- Обоснования версий общие («соответствует семантическому версионированию»), без привязки к содержанию.

Тестовые коммиты синтетические, поэтому по реальному качеству на настоящей истории проекта эти прогоны выводов не дают.

## Что не запускалось и ограничения

- Реальный релиз репозитория проекта не выполнялся: он делается один раз на видео и не входит в контрольные прогоны (D-15).
- Облачные модели не проверялись (D-16): все прогоны на локальной `qwen/qwen3.5-9b`.
- Контрольный прогон — один успешный итоговый; повторяемость на нескольких запусках не измерялась. Предшествующие прогоны падали по описанным выше причинам, поэтому нестабильность модели остаётся реальным риском.
- Качество changelog проверено только на синтетической истории тестовой песочницы.
- Минорный формат сообщения тега (A1) не подтверждён пользователем.

## Подготовка к видео

1. Привести рабочее дерево проекта в чистое состояние. Правило строгое: неотслеживаемые файлы тоже блокируют релиз (сейчас это, например, `eval_out/day33*`, `.planning/.pending-auth-captures.jsonl` и изменённый `.planning/HANDOFF.json`).
2. Добавить запись `release-git` (встроенный `project_git.py` с `--allow-release`, корень — репозиторий проекта) и указать в её окружении `GITHUB_PERSONAL_ACCESS_TOKEN` — токен именно для репозитория проекта.
3. Убедиться, что push в `origin` работает по SSH без запроса пароля.
4. Включить локальную модель в LM Studio (желательно `qwen/qwen3.5-9b`). Генерация changelog занимает около минуты.
5. В чате выполнить `/release`, показать план (диапазон, версия, название, changelog), нажать «Подтвердить релиз», показать четыре шага и ссылку на черновик Release.
